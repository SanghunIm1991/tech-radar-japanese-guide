# Thoughtworks Technology Radar の技術を日本語で解説する公開リポジトリ

## 概要・きっかけ

IT業界の技術トレンドを追うため、Thoughtworks が発行している **Technology Radar**（https://www.thoughtworks.com/radar）に載った技術を、日本語で解説する資料集を作り、GitHub で**公開**する。

- **粒度**: システムアーキテクト向けの粒度（想定する読者の立場）。1項目につき**10分程度**で読める基本的な内容にとどめ、本当に必要になったときに深掘りする（深掘りの入口となる一次情報のリンクを付ける）
- **更新**: 定期的に更新する。Radar は約半年ごとに発行され（発行時期の例: 2025年4月に Vol.32、2025年11月に Vol.33。2026-11-08 時点の検索結果による。これは例で、最新の版ではない可能性が高い。最新の版は着手時に確認する）、版ごとに項目の追加やリングの移動がある
- **Radar の構成**（Claude の認識。着手時に公式サイトで確認する）: 1つの項目を「blip」と呼び、4つの象限（Techniques／Tools／Platforms／Languages & Frameworks）と、4つのリング（Adopt／Trial／Assess／Hold。採用を勧める度合い）に配置される。各版には、その版で目立った傾向をまとめた「テーマ」が数個付く

## 評価

- **良い点**
  - Radar は実案件での経験に基づく評価で、技術そのものだけでなく「採用してよい段階か」という判断の目安が付いている。アーキテクトが技術選定の候補を知る入口として使いやすい
  - 公式の日本語版（過去の版を含む）の有無は、2026-11-08 時点の2回の検索では確認できなかった（無いとまでは言えない。着手時に公式サイトの言語の切り替え等で改めて確認する）。日本語の解説記事は過去の版（2011〜2015年頃）を扱うものが見つかったが、版ごとに項目単位で継続的に解説する資料は少ないと見込まれる（着手時に改めて確認する）
  - 「1項目10分・基本だけ」と粒度を決めているので、1ファイルの分量と書き方をそろえやすい
- **懸念点**
  - **分量**: 1つの版に載る項目は多い（Claude の認識では100前後。要確認）。全項目を10分ずつ解説し、版ごとに更新するのは手間が大きい。対象の絞り込みが必要（実現方針の分岐点1）
  - **著作権**: Radar の各項目の説明文を翻訳して載せると、Thoughtworks の文章の二次的著作物になる。翻訳はせず、技術そのものの解説は各技術の公式ドキュメント等の一次情報をもとに自分の言葉で書き、Radar での評価は短い要旨と元のページへのリンクにとどめる。Radar のサイトの利用条件は着手時に確認する。Radar の図（レーダーの画像）やロゴも転載しない
  - **公式との誤認**: 「Thoughtworks」「Technology Radar」の名称を使うため、公式の翻訳や公式の関連物と誤解されないよう、README に非公式である旨を明記し、リポジトリ名にも公式を想起させる表現を避ける
  - **1社の見解であること**: Radar は Thoughtworks の見解で、業界全体の総意ではない。解説では「Thoughtworks はこう評価している」と主語をはっきりさせ、他の見方があればそれも添える
  - **鮮度**: リングは版ごとに変わる。技術そのものの解説（あまり古くならない部分）と、Radar での評価（版ごとに変わる部分）を分けて書き、後者には版と確認日を付ける
  - **AI が書いた内容であること**: 解説は Claude Code が下書きする想定のため、もっともらしい誤りが混ざりうる。ユーザーが確認したうえで公開し、Claude Code が下書きした旨を README に明記するかを着手時に決める
  - **公開に伴う点検**: 公開前と push 前に、機密情報・個人情報・第三者の著作物の混入を点検する。自分たちが書いた文章のライセンス（例: CC BY 4.0）も決めて明示する

## 肉付け（想定する構成）

- **README**: 解説集の目的、非公式である旨、Radar の読み方（象限とリングの意味）、各解説の読み方、ライセンス
- **技術ごとの解説ファイル**（1項目 = 1ファイル。版をまたいで同じファイルを更新する案）。そろえる見出しの案:
  1. 一言でいうと
  2. 解決する課題（なぜ生まれたか）
  3. 仕組みの概要
  4. アーキテクチャ上の位置づけとトレードオフ（どこに効くか、何を代償にするか）
  5. 採用を判断するときの観点
  6. 関連技術・代替技術
  7. Radar での扱い（版ごとのリングの推移、Thoughtworks の評価の要旨とリンク）
  8. 深掘りするときの一次情報（公式ドキュメント等）
  9. 確認日
- **版ごとの索引**: その版のテーマの要旨と、新規・移動した項目の一覧（各解説へのリンク）
- **分量の目安**: 10分で読める分量は、日本語でおおよそ3,000〜4,000字（1分あたり400〜600字で読むとした Claude の見立て）。図が要る場合は mermaid で自作する

## 実現性

技術的な難易度は低い。Markdown と GitHub だけで作れる。難しいのは、(1)項目数の多さと、版ごとの更新の手間、(2)解説の正確さの裏取り、(3)著作権の線引き（翻訳せず自分の言葉で書く、評価は要旨とリンクにとどめる）。(1)は、解説を書く手順（調べる情報源・見出し・点検項目）を Claude Code のスキルにまとめ、版が出るたびに同じ手順で回すと負担を減らせる見込み。

## 実現方針（案）

分岐点1・2・4・5は決定済み（2026-11-08、ユーザーの回答）。分岐点3と、GitHub Pages の作り方の細部（下の節の分岐点P1）は未決で、着手時に決めて `docs/qa_log.md` に記録する。

- **分岐点1: 解説する項目の範囲**
  - 選択肢A: その版の全項目
  - 選択肢B: 新規に載った項目と、リングが移動した項目だけ（版ごとの差分を追う）
  - 選択肢C: Adopt と Trial の項目だけ（実際に採用されやすいもの）
  - 選択肢D: 関心のある象限・分野から選ぶ
  - **決定: A（分野は絞らない）**。目的は広く浅く知ること。2つめ以降の版では、新規の項目は新しく書き、既存の項目は Radar での扱い（リングの推移・評価の要旨）を更新する
  - 注意: 全項目だと、1つの版で100前後（要確認）の解説を書くことになる。Claude の案: 一度に全部をそろえてから公開するのではなく、象限ごと等の区切りで書き上げた分から順に公開する（区切り方は着手時に決める）
- **分岐点2: どの版から始めるか**
  - **決定: 着手時点の最新版から始める**。過去の版にはさかのぼらない（各項目の「Radar での扱い」には、分かる範囲で過去のリングの推移を書いてよい）
- **分岐点3: 解説の単位**: 技術ごとに1ファイルにして版をまたいで更新するか（上の構成案）、版ごとにファイルを分けるか（未決）
- **分岐点4: 更新の進め方**
  - **決定: 新しい版が出たら、ユーザーが Claude Code に更新を依頼する**。定期実行での自動確認はしない
  - 依頼のたびに書き方がぶれないよう、解説を書く手順をスキルにまとめるかは着手時に決める
- **分岐点5: 公開の形**
  - **決定: GitHub Pages を試す**（サイトとして読めるようにする）。詳細は次の節
- **着手時に確認すること**: Radar のサイトの利用条件、最新の版と項目数、公式の日本語版の有無、リポジトリ名と文章のライセンス

## GitHub Pages での公開（案）

GitHub Pages は、GitHub のリポジトリに置いたファイルから、静的な Web サイトを無料で公開できる GitHub の機能。手順を追いやすいよう、実現用のプロジェクトでは手順を1つずつ確かめながら進め、その手順を手順書として残す（ユーザーの希望）。以下は Claude の認識に基づく案で、仕様・制限は着手時に GitHub の公式ドキュメント（docs.github.com）で確認する。

- **基本の仕組み**
  - 公開される URL は `https://<GitHubのユーザー名>.github.io/<リポジトリ名>/` の形になる（ユーザー名が URL に出る）
  - 無料のプランでは、Pages を使えるのは public のリポジトリに限られる（認識。要確認）。今回は公開が前提なので問題にならない
  - サイトの内容は誰でも見られる。リポジトリと同じく、機密情報・個人情報・第三者の著作物を載せない
  - 公開の元を「ブランチから」（例: `main` ブランチの直下か `docs/` フォルダ）と「GitHub Actions から」の2通りから選べる
  - サイズや転送量に上限がある（認識: サイト1GB まで等。要確認）。テキスト中心なら問題になりにくい
- **分岐点P1: サイトの作り方**（未決。着手時に決める）
  - 選択肢A: **Jekyll（GitHub 標準）をそのまま使う**。Markdown を置いて設定画面で公開元を選ぶだけで、GitHub 側がサイトに変換する。手元に新しいツールを入れなくてよい。一方、項目が100を超えると、目次・検索・象限ごとの絞り込みを作り込む手間が出る。mermaid の図はそのままでは描画されない可能性がある（要確認）
  - 選択肢B: **ドキュメント用の静的サイト生成ツール**（例: MkDocs と Material for MkDocs）を GitHub Actions で動かす。サイドメニュー・検索・タグ付けがそろっていて、項目の多い解説集に向く。設定ファイルと Actions のワークフローを書く手間が増え、手元で表示を確かめるには Python のツールの導入が要る（導入するかはその時点で確認する）
  - Claude の案: まず A で「公開できた」ことを確かめて仕組みに慣れ、項目が増えて探しにくくなったら B へ移る。移っても Markdown の本文はほぼそのまま使える
- **手順の骨子**（選択肢A の場合。細部は着手時に公式ドキュメントで確認する）
  1. public のリポジトリを作る（作る前に `public-release-review` スキルに沿って点検する）
  2. トップページ（`index.md` または `README.md`）と、試しに解説を1〜2項目置いて push する
  3. リポジトリの Settings → Pages で、公開元のブランチとフォルダを選んで保存する
  4. Actions タブで、サイトの構築が終わるのを待つ（数分）
  5. 表示された URL を開き、表示・リンク・日本語の文字化けがないかを確かめる
  6. 問題がなければ、残りの項目を区切りごとに追加していく
- **注意**
  - 手元で表示を確かめるために Ruby（Jekyll）等を入れる必要は、選択肢A では基本的にない。push して GitHub 側の表示で確かめる
  - 下書き中の解説を誤って公開しないよう、公開しない下書きの置き場所（別ブランチ、またはサイトの構築から外すフォルダ）を決めておく
