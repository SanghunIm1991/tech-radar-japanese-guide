ODCSOpen Data Contract Standard

名前の手がかり: Open 開かれた・公開された ＋ Data データ ＋ Contract 契約 ＋ Standard 標準

データを渡す側と使う側が「どんな形・品質・頻度のデータを渡すか」を取り決めたデータ契約を、YAML で書くためのオープンな標準

たとえるなら（筆者の見立て）

Web の API の仕様を書く OpenAPI の「データ版」

表の列の名前や型だけでなく、「空の値は何件まで」「毎日何時までに更新」といった約束まで、1つのファイルに書きます。

2つの課題と、ODCS の答え

課題と、その答えを対で並べています。課題の多くは筆者の見立てです。

出す側が列の名前や意味を変え、使う側の集計が黙って壊れる

機械で確かめられない取り決め

取り決めが口頭や表計算のファイルにしかないと、どこが壊れるのか事前に分からず、機械で確かめることもできない（筆者の見立て）。

ODCS の答え

スキーマ・品質のルール・SLA を1つの YAML に書き、道具で検査できるようにする

書き方の誤りは JSON Schema で見つけられる。Data Contract CLI を使えば、契約を実データに当てて検査し（test）、契約の変更が使う側を壊すかを判定できる（breaking）。標準そのものは書式を決めるもので、検査は道具が行う。事故を防げるのは、検査を変更の流れに組み込んだとき（筆者の見立て）。「試してみる」の図で試せます。

取り決めの書き方がばらばらだった

データメッシュ（data mesh）で重要になる取り決め

データを「製品」として各部門が提供するデータメッシュが広がると、取り決めがいっそう重要になる（筆者の見立て）。Thoughtworks も、競合する書式や各組織が独自に作った書式が並んでいたと述べている。

ODCS の答え

特定の会社でなく、Linux Foundation AI & Data の下のプロジェクトが管理する共通の標準

Linux Foundation AI & Data の下の Bitol が管理するオープンな標準。別の書式だった DCS は、ODCS の v3.1.0 の公開に合わせて非推奨になり、ODCS への移行が勧められている。対応を表明している製品の一覧もある。Thoughtworks も、ODCS が主要な標準として定着してきたと見ている。

試してみる: 出す側が変えたことは、どこで分かるか

課題1への答えを確かめる図です。出す側に起きた変更と、契約の有無を選ぶと、それがどこで分かるかが変わります。注文のデータの例と、変更の種類は説明のための例です。「契約あり」は、契約を実データに当てる検査（Data Contract CLI の test）を、変更の流れ（CI など）に組み込んだ場合です（組み込み方は筆者の見立て）。

1つの契約のファイルに書くこと

主な節です。標準は Linux Foundation AI & Data の下の Bitol が管理し、確認日の時点の最新版は v3.2.0（標準そのものは Apache-2.0 ライセンス）。書いた YAML を確かめるための JSON Schema もあり、エディタに読み込ませて間違いを見つけられます。

基本Fundamentals契約の ID・版・状態・担当する領域・目的や使い方の説明
スキーマSchema表やオブジェクトと、その項目の名前・型・必須か・主キーか・例など
データ品質Data Quality品質のルール。4種類で書ける
SLA更新の頻度・遅れの許容・保存期間などの約束。「何を」「いくつ」「どの単位で」の組で書く。推奨の項目名は latency・retention・frequency・availability など
サーバーServersデータの置き場所。PostgreSQL・S3・Kafka・Snowflake といった多くの種類を指定できる
そのほか担当チーム・役割（権限）・問い合わせ先・料金・独自の項目など

品質のルールの4種類

text人が読むための説明だけ
library標準で決められた指標（空の値の数 nullValues・重複 duplicateValues・行数 rowCount など）を、mustBe（〜でなければならない）・mustBeLessThan（〜より小さい）といった比べ方で書く
sql数（または真偽値）を返す SQL を書き、その結果を同じ比べ方で判定する
customSoda や Great Expectations など、特定の品質検査の道具の書き方をそのまま埋め込む

ごく小さな例（主な項目だけを抜き出した、説明用の簡略版）

apiVersion: v3.2.0
kind: DataContract
id: orders-contract
version: 1.0.0
status: active
schema:
  - name: orders
    logicalType: object
    properties:
      - name: order_id
        logicalType: string
        required: true
        primaryKey: true
      - name: amount
        logicalType: number

v3.0.0（2024年10月）では、columns が properties に、isNullable が required に変わるなど、多くの項目が改名・削除されました。v2 の書き方はそのままでは通らず、後方互換性がありません。

得るもの

  • 機械で確かめられる: 契約に書いたスキーマや品質のルールを、道具で実データに当てて検査できる
  • 道具をまたいで使える: 標準の書式なので、特定の製品に縛られにくい。対応を表明している製品の一覧もある（網羅的ではない一覧）
  • 人にも AI にも読める: 宣言的な書き方なので、人と AI エージェントの両方が読み、確かめやすいと Thoughtworks は評価している

代わりに失うもの・注意点

  • 書いて守る手間: 契約を書くこと自体は品質を上げない。検査を流れに組み込み、破ったときに誰が直すかを決めて初めて効く（筆者の見立て）
  • 版の変化: v2 から v3 で多くの名前が変わり、v3.1.0 でも JSON Schema の一部に互換性の無い変更があった。契約のファイルの版をそろえ、道具の対応状況を確かめる必要がある
  • 組織の合意が要る: 出す側が契約に責任を持つ体制が無いと、書いた契約が古いまま放置される（筆者の見立て）

導入するときに考える5つのこと

使うかどうか、どう入れるかを考えるための観点を、詳しい解説の第5節から並べました（筆者の整理）。

出す側と使う側は分かれているか？

データを出すチームと使うチームが分かれていて、変更による事故が起きているなら効果が大きい。1つのチームが作って自分で使うだけなら、手間に見合わないこともある（筆者の見立て）。

今の書式から移るか？

以前の Data Contract Specification（DCS）は、ODCS の v3.1.0 の公開に合わせて非推奨になり、ODCS への移行が勧められている。Data Contract CLI には DCS から ODCS へ変換する書き出しの機能がある。

どの道具で検査するか？

オープンソース（MIT）の Data Contract CLI は ODCS に対応し、書式の検査（lint）、実データとの照合（test）、変更が互換性を壊すかの判定（breaking）、ほかの書式への書き出し（export）などができる。

今の品質検査の道具とどう分けるか？

すでに Soda や Great Expectations を使っているなら、custom のルールでその書き方を契約に取り込める。

費用と依存先は？

標準も主な道具もオープンソースで、費用は主に書いて運用する人の手間。商用の製品を使う場合は、その製品の対応する ODCS の版を確かめる（筆者の見立て）。

関連技術・代替技術

ODPS

Open Data Product Standard。同じ Bitol が管理する、「データ製品」そのものを記述する標準。ODCS とそろえて作られ、データ製品とデータ契約を結び付けることを狙う。Thoughtworks は、データメッシュやデータ製品を作る顧客の中で、ODPS とあわせて ODCS へ移る例が多いとしている。

Data Contract CLI

ODCS を扱うオープンソースの道具。契約の検査・実データとの照合・互換性の判定・書き出しができる。

OpenAPI・AsyncAPI

API や非同期のメッセージの仕様を書く標準。ODCS はデータの受け渡しの側で同じ役割を果たす（筆者の見立て）。

Soda・Great Expectations

データの品質を検査する道具。ODCS の品質のルール（custom）に、その道具の書き方を埋め込める。

データ契約

data contract ＝ データの契約

データを渡す側と使う側の間で、データの形・意味・品質・更新の頻度などを取り決めたもの。機械で確かめられる形で書くことが多い。

YAML

YAML ＝ YAML Ain't Markup Language（YAML はマークアップ言語ではない）

字下げで階層を表す、人が読み書きしやすい設定ファイルの書式。

スキーマ

schema ＝ 図式・枠組み

データの構造の定義。どんな項目があり、それぞれがどんな型か、必須かなどを決めたもの。

データメッシュ

data mesh ＝ データの網の目

データを1か所に集めて中央のチームが管理するのではなく、各部門が自分のデータを「製品」として責任を持って提供する考え方。

SLA

SLA ＝ Service Level Agreement（サービスの水準の合意）

提供する側が守ると約束するサービスの水準（更新の頻度・遅れ・可用性など）。

JSON Schema

JSON ＝ JavaScript Object Notation（JavaScript のオブジェクトの表記） ／ schema ＝ 枠組み

JSON（や YAML）のデータが決められた形になっているかを、機械で検査するための定義の書き方。

後方互換性

backward ＝ 後ろ向きの・前の版への ／ compatibility ＝ 互換性

新しい版が、古い版の書き方のファイルをそのまま受け付けられること。無い場合は書き直しが要る。

宣言的

declarative ＝ 宣言の・宣言的な

手順ではなく、「どうあるべきか」という結果の状態だけを書く書き方。

主キー

primary key ＝ 主な鍵

表の中で、1行を一意に見分けるための項目。

CI

CI ＝ Continuous Integration（継続的な統合）

変更のたびに自動でビルドや検査を行う仕組み。
