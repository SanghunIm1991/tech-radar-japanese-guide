## 1. 一言でいうと

**名前の手がかり**: Git〈この道具が拡張する、バージョン管理の道具の名前〉＋ AI〈Artificial Intelligence（人工知能）の略〉

Git AI は、リポジトリの中の「AI が書いたコード」を1行ずつ記録する、**Git** の拡張です。AI が書いた行ごとに、それを書いた**エージェント**（Claude Code や Cursor など）・**モデル**・セッションを結びつけて残します。オープンソースで、ライセンスは Apache-2.0 です（[GitHub の README](https://github.com/git-ai-project/git-ai)）。

たとえるなら、共同で書いた原稿の1行ずつに「この行は誰が、どの下書きの相談から書いたか」の付箋を貼っておくようなものです。原稿そのものには手を加えず、付箋だけを別に貼ります。

## 2. 解決する課題（なぜ生まれたか）

AI のコーディングエージェントにコードを書かせる開発が広がり、リポジトリの中で AI が書いた部分が増えています。Thoughtworks は、エージェントが書くコードが増える中で、コードの元の意図や設計の判断をあとから問い合わせられる点を評価しています（[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/git-ai)）。その背景には、次の課題があります。

- **どの行を AI が書いたのかが分からない**: Git の履歴には、誰が書き、誰がコミットしたかが残ります。しかし人がエージェントの出力をまとめてコミットすると、どの行が AI の書いたものかは残りません
- **書いた理由をあとから追えない**: コードを書いたときの指示（**プロンプト**）や会話の流れは、エージェントの画面の中にしか残らず、あとから意図や設計の判断を確かめられません
- **履歴を整えると記録が崩れる**: **rebase** や **squash**（複数のコミットを1つにまとめること）でコミットを作り直すと、コミットに付けた情報は失われやすくなります

## 3. 仕組みの概要

### 課題ごとの答え

| 課題 | Git AI の答え |
|---|---|
| どの行を AI が書いたのかが分からない | エージェントが、コードを書くたびに自分で「この行を書いた」と報告する（**チェックポイント**）。AI らしさを推測して見分けるのではなく、エージェントの報告をそのまま記録する。コミットのときに、行ごとの記録を残す（[README](https://github.com/git-ai-project/git-ai)）。Thoughtworks は、行を足した時点で数えるだけの方法より細かく記録できる点を挙げている（[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/git-ai)） |
| 書いた理由をあとから追えない | 行ごとに、書いたエージェント・モデル・セッションを結びつける。会話の記録そのものは Git の外に置く（後述）。Thoughtworks は、保管したセッションを使って、人もエージェントも、コードの元の文脈や設計の判断を問い合わせられる点を挙げている（[README](https://github.com/git-ai-project/git-ai)、[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/git-ai)） |
| 履歴を整えると記録が崩れる | rebase・cherry-pick・squash・amend・reset などの操作のあと、最終的なコードの状態を調べて、記録を新しいコミットに写し直す。push と fetch で、記録をリモートと同期する（[README](https://github.com/git-ai-project/git-ai)） |

### 記録の置き場所: Git Notes

記録は **Git Notes** に置きます。Git Notes は、コミットそのものを書き換えずに、コミットに付加情報を付ける Git の標準の仕組みです（[git-notes](https://git-scm.com/docs/git-notes)）。コミットの識別子（ハッシュ）は変わらないので、既存の履歴を壊しません。

記録の形式は、公開された仕様（v3.0.0）で決められています。記録は `refs/notes/ai` という専用の置き場所に入れ、Git の既定の置き場所は使いません。中身は「AI が書いた行の範囲（例: `1-5`）」と、エージェントの種類やモデルなどを書いた JSON の2つの部分からなります。プロンプトの本文は、v1.3.4 から記録に入れない決まりになりました。代わりに、Git の外に置いた会話の記録へのリンクを、任意で残せます（[仕様 v3.0.0](https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md)）。

### エージェントとのつなぎ方

Git AI は、各エージェントの「道具を使う前・後」に呼ばれる仕組み（**フック**）を自分で設定・更新します。リポジトリごとの設定や Git のフックは要らず、Git のコマンドを包んで置き換えることもしないと README は説明しています。対応するエージェントとして、Claude Code・Codex・Cursor・GitHub Copilot・OpenCode・Windsurf・Gemini などが挙がっています（[README](https://github.com/git-ai-project/git-ai)、[公式サイト](https://usegitai.com/)）。

### 記録の使い方

- `git ai blame`: `git blame`（各行を最後に変えたコミットを表示するコマンド）の代わりに使え、各行が AI のものかを表示する
- `git ai stats`: AI が書いた行の割合、AI が出した行のうちコミットされた行の割合などを集計する

（[README](https://github.com/git-ai-project/git-ai)）

### 無料の CLI とチーム向けの版

手元で動く CLI は無料・オープンソースで、ログインなしに動きます。チーム向けの版は、プロンプトを安全に保管する場所や、プルリクエスト・チームごとの AI の割合やトークンの費用の集計を足すもので、自社で動かすか、開発元のクラウドで使えます（[公式サイト](https://usegitai.com/)）。会話の記録は、秘密の情報を消す処理をしたうえで Git の外に保存すると README は書いています（[README](https://github.com/git-ai-project/git-ai)）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: バージョン管理の上に「AI の関与の記録」の層を足す道具です。コードそのものや開発の流れは変えず、記録を横に添えます。

**代わりに失うもの・注意点**

- **エージェントの報告が頼り**: 記録はエージェントからの報告に基づくので、対応していないエージェントや、報告の届かない書き方では抜けます。README は、エージェントが bash でファイルを作るとき、リポジトリの最上位以外の場所で作業していると、うまく記録できないことがあると書いています。ファイルの名前を変えると（`git mv`）、記録はついていきません（[README](https://github.com/git-ai-project/git-ai)）
- **ホスティングの側のまとめ方**: GitHub などの画面で「Squash and Merge」や「Rebase and Merge」を使う場合、記録を保つには、チーム向けの版か、オープンソースの CI の仕組みが要ります（[README](https://github.com/git-ai-project/git-ai)）
- **記録に人の情報が入る**: 仕様では、AI に指示した人（例としてメールアドレス）を任意で記録に含められるほか、人が書いた行の記録には、コミット者の名前とメールアドレスが入ります。記録は push でリモートと同期されます（[仕様 v3.0.0](https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md)、[README](https://github.com/git-ai-project/git-ai)）。筆者の見立てでは、公開のリポジトリでは、誰がどのエージェントを使ったかまで公開されうるので、入れる前に記録の中身を確かめておくべきです
- **入れ方**: README の手順は、Web からスクリプトを取ってそのまま実行する形です（[README](https://github.com/git-ai-project/git-ai)）。筆者の見立てでは、会社の端末では、配布されているインストーラーや管理の仕組みを使うかを、管理者と相談するのが安全です
- **仕様と開発元の変化**: 仕様は版を重ねており、綴りの誤りがある項目の名前を、次の大きな版（v4）で直すと予告しています（[仕様 v3.0.0](https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md)）。また公式サイトには「Git AI is now part of OpenAI」という表示があります（[公式サイト](https://usegitai.com/)。詳しい経緯はこの解説では確かめていません）。筆者の見立てでは、特定のエージェントの開発元に近い道具になることが、ほかのエージェントへの対応の続き方にどう響くかは、見守る必要があります

## 5. 採用を判断するときの観点

- **目的をはっきりさせる**: レビューで AI が書いた行を重点的に見たいのか、AI の使い方の傾向を知りたいのか。筆者の見立てでは、AI の割合の数字を、開発者個人の評価に使うと、記録を避ける動きを生みかねません
- **使っているエージェント**: チームのエージェントが対応の一覧に入っているか
- **マージのやり方**: ホスティングの画面で squash や rebase でまとめる運用なら、記録を保つための追加の仕組みが要る
- **公開範囲**: 公開のリポジトリで記録を push してよいか。人の情報を含めるか
- **始め方**: 筆者の見立てでは、1つのリポジトリで CLI を入れ、`git ai blame` や `git ai stats` の結果が実感と合うかを確かめてから広げる

## 6. 関連技術・代替技術

- **git blame**: 各行を最後に変えたコミットと作者を表示する、Git の標準のコマンド。Git AI の `git ai blame` は、その代わりに使える形で AI の情報を足す（[README](https://github.com/git-ai-project/git-ai)）
- **Git Notes**: コミットを書き換えずに付加情報を付ける Git の標準の仕組み。Git AI の記録の置き場所（[git-notes](https://git-scm.com/docs/git-notes)）
- **コミットメッセージに AI の関与を書く慣行**: コミットの単位で、AI が関わったことを書き添える方法（一般的な説明）。行の単位は分からない
- **Git AI の標準**: 仕様は、Git Notes に同じ形式の記録を付けるほかの実装も、この標準に沿うものと見なすと書いている（[仕様 v3.0.0](https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md)）
