## 1. 一言でいうと

Agent Package Manager（APM）は、AI のコーディングエージェントに読ませる設定、つまり指示文・スキル（作業の手順書）・プロンプト・MCP サーバー（エージェントに外部のツールをつなぐ部品）などを、**npm や pip のようなパッケージマネージャーと同じ形で、宣言してインストールし、版を固定して管理する**ためのオープンソースの道具です。Microsoft の GitHub の組織で公開されています（[GitHub: microsoft/apm](https://github.com/microsoft/apm)）。

たとえるなら、チームのメンバーが各自の机に手書きのメモを貼り合うのをやめ、版の付いた共有の手引書を棚から取り寄せる仕組みにするようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

コーディングエージェントを使うチームでは、エージェント向けの指示文やスキルのファイルが増えていきます。これを各リポジトリへコピー＆ペーストで配ると、次のような問題が起きます（筆者の見立て）。

- どのリポジトリにどの版が入っているか分からなくなる
- 元のファイルを直しても、コピー先に反映されない
- 出どころの分からないファイルが紛れ込み、中に悪意のある指示が隠れていても気づきにくい

Thoughtworks のチームは、ファイルのコピーをやめ、中央のリポジトリから版の付いたスキルを配るために APM を使っているとしています。エージェントに渡す文脈を、ソフトウェアの部品と同じ「サプライチェーン」（部品が作られて届くまでの流れ）として扱う考え方です（[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/agent-package-manager)）。

## 3. 仕組みの概要

**マニフェストとロックファイル**（[GitHub: microsoft/apm](https://github.com/microsoft/apm)。この項の出典は同じ）

- **マニフェスト（`apm.yml`）**: 使いたいパッケージを宣言するファイルです。名前・版・対象のエージェント（`targets`）に加えて、`dependencies` の下に、スキルやプラグインをリポジトリのパスやタグで書き、MCP サーバーを名前と接続の方式で書きます
- **ロックファイル（`apm.lock.yaml`）**: 実際に解決された依存の全体を固定するファイルです。npm の `package-lock.json` と同じ役割で、取得元と中身のハッシュ（内容から計算する指紋のような値）を記録します。同じロックファイルからは、誰が入れても同じ中身になります

**管理できるもの**: 指示文、スキル、プロンプト、エージェントの定義、フック、プラグイン、MCP サーバーです。パッケージがほかのパッケージに依存していても、APM が依存の全体（推移的な依存）を解決します。

**取得元**: GitHub、GitLab、Bitbucket、Azure DevOps など、どの Git のホストからでも取得できます。プラグインのマーケットプレイス（配布の場）を登録して、そこから入れることもできます。

**対応するエージェント**: README は、GitHub Copilot、Claude Code、Cursor、OpenCode、Codex、Gemini、Windsurf などを挙げています。たとえば `apm compile -t copilot` で、Copilot 向けの指示文のファイル（`.github/copilot-instructions.md`）を作ります。

**主なコマンド**

| コマンド | 役割 |
|---|---|
| `apm install` | マニフェストに書いた依存をすべて入れる |
| `apm compile` | 対象のエージェント向けのファイルを作る |
| `apm audit` | インストールのときと同じ安全の検査を、あとから実行する |
| `apm lock export --format cyclonedx` | 依存の一覧を SBOM として書き出す（spdx も可） |

**安全のための機能**

- **見えない文字の検査**: `apm install` のたびに、エージェントの動きを乗っ取りうる、目に見えない Unicode の文字が無いかを調べ、問題のあるパッケージをエージェントが読む前に止めるとしています
- **ずれの検出**: `apm audit` は、入れたファイルが手で書き換えられていないか（ドリフト）も調べます
- **ポリシー**: `apm-policy.yml` で、許可する取得元・範囲・部品の種類を組織として決め、`apm install` のときに守らせます。企業→組織→リポジトリの順に、厳しくする方向にだけ引き継がれます
- **SBOM**: CycloneDX と SPDX の形式で書き出せます。README は、これは調達のための出どころの情報で、法令などを満たしていることの証明ではないと断っています
- **MCP サーバーの同意**: 依存の先から間接的に入る MCP サーバーは、明示的に同意しないと入りません

**版**: 確認日の時点の最新は v0.35.1 で、1.0 より前の段階です（[GitHub: microsoft/apm のリリース](https://github.com/microsoft/apm/releases)）。ライセンスは、ソフトウェアが Apache 2.0、ドキュメントが CC BY 4.0 です。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: エージェントの「文脈」の依存関係の管理です。アプリのコードでライブラリを npm や Maven で管理するのと同じ考え方を、エージェントに渡す指示やスキルに当てはめたものです（筆者の見立て）。Thoughtworks は、これにより企業全体で使うエージェントの環境（ハーネス）を、再現でき、統制の効いた形にできるとしています（[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/agent-package-manager)）。

**得られるもの**

- **再現性**: ロックファイルで、どのリポジトリでも同じ版の指示やスキルが使われる（README）
- **出どころの追跡**: ハッシュと取得元の記録、SBOM の書き出しで、何がどこから来たかをたどれる（README）
- **統制**: ポリシーで、許可していない取得元のパッケージを入れられないようにできる（README）

**代わりに失うもの・注意点**

- **若さ**: 1.0 より前の段階で、コミュニティが主導するプロジェクトである（大手の企業が支援している）。Radar もこれを理由に Trial にとどめ、競合する仕組みが出てくることも予想している（[Radar のページ](https://www.thoughtworks.com/en-us/radar/tools/agent-package-manager)）。1.0 より前なので、仕組みが変わる可能性がある（筆者の見立て）
- **もう1つの道具**: npm などとは別に、APM 自体の導入と更新、チームへの浸透が要る（筆者の見立て）
- **検査の限界**: 見えない文字の検査で、文章として書かれた悪意のある指示まで見抜けるとは限らない。中身を読んで確かめる手順は残る（筆者の見立て）

## 5. 採用を判断するときの観点

- **規模**: エージェント向けの指示やスキルを、複数のリポジトリやチームで共有しているか。1つのリポジトリだけなら、ファイルを直接置くほうが簡単（筆者の見立て）
- **使っているエージェント**: 使っているエージェントが、APM の対応先に入っているか（README）
- **統制の要否**: 取得元の制限や監査、SBOM が、社内の決まりとして求められているか（筆者の見立て）
- **変化への備え**: 1.0 より前の道具なので、版の上げ方と、乗り換えになったときに戻せる形（ふつうのファイルとして残るか）を確かめる（筆者の見立て）
- **出どころの確認**: 外部のパッケージを入れる前に、中身を読む手順を決めておく（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| パッケージマネージャー | ソフトウェアの部品（パッケージ）を、宣言どおりに取り寄せて入れ、版を管理する道具。npm や pip など |
| マニフェスト | 使いたいパッケージとその版を宣言するファイル |
| ロックファイル | 実際に入れたパッケージの版と中身を固定して記録するファイル。同じ中身を再現できる |
| 推移的な依存 | 使うパッケージが、さらに別のパッケージに依存していること。その先まで含めた依存 |
| ハッシュ | ファイルの中身から計算する短い値。中身が少しでも変わると値が変わるので、改ざんの確認に使う |
| スキル | エージェントに特定の作業のやり方を教える、手順書のようなファイル |
| MCP | エージェントに外部のツールやデータをつなぐための共通の仕組み（Model Context Protocol） |
| サプライチェーン | 部品が作られ、配られ、組み込まれるまでの流れ。途中で悪意のある部品が紛れ込む攻撃がある |
| SBOM | ソフトウェアに含まれる部品の一覧（Software Bill of Materials）。CycloneDX や SPDX という形式がある |
| Unicode | 世界中の文字を扱うための文字の決まり。目に見えない制御用の文字も含む |
| ドリフト | 決めた状態から、手作業の変更などで少しずつずれていくこと |
| ポリシー | 何を許し、何を禁じるかを決めた決まり |
