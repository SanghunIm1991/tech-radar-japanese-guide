mise

名前の手がかり: mise フランス語の mise en place（ミザンプラス。料理の前に、材料や道具をそろえて配置しておくこと）から。読みは「ミーズ」

プロジェクトで使う開発ツールの版・環境変数・よく使うコマンド（タスク）を、1つの設定ファイル mise.toml にまとめて管理するコマンドラインの道具

たとえるなら

フォルダに「この料理にはこの包丁とこの鍋」のメモを置くと、入っただけで道具が持ち替わる

メモにあたるのが、プロジェクトのフォルダに置く設定ファイル mise.toml です。道具にあたるのは、Node.js や Python などの開発ツールの版です。

3つの課題と、mise の答え

課題と、その答えを対で並べています。

プロジェクトごとに版が違い、行き来するたびに入れ替えが要る

版（version）

Node.js の 20 系と 24 系のように、必要な版はプロジェクトごとに違う。1台の PC に1つの版しか入れられないと、行き来するたびに入れ替えが要る。

mise の答え

複数の版を並べて入れ、フォルダの設定どおりに切り替える

今いるフォルダの mise.toml に書かれた版を使う。activate ならフォルダを移動したときに、shim なら呼ばれるたびに PATH が切り替わるので、入れ替えの作業は要らない。下の図で試せます。

言語ごとに別のバージョンマネージャーを覚えるのは手間

バージョンマネージャー（version manager）

Node.js の nvm、Python の pyenv、Ruby の rbenv、Rust の rustup と、言語ごとに道具がある。これをまとめる道具として asdf が広まった。

mise の答え

1つの道具で、多くの言語と CLI ツールを扱う

入手先を「バックエンド」という部品に分け、多くのツールを1つの道具で扱う。asdf の .tool-versions も読めるので、プロジェクトごとに移せる。Thoughtworks も今回の版で、既存の言語ごとの道具と並べて使えるので、一度にすべてを移す必要はないとしている。

手元では動くのに、CI では動かない

CI（Continuous Integration）

開発者と CI で使う版が違うと、こうした食い違いが起きる。

mise の答え

設定とロックファイルを Git で共有し、CI でも同じ版を入れる

mise.toml と mise.lock を Git で共有し、mise install --locked で入れると、ロックファイルと違う版は入らない。CI では公式のアクション（jdx/mise-action）が mise.toml のツールを入れ、mise.lock があれば --locked で入れる。ただし、そろうのはツールの版までで、OS のライブラリの違いは残る。下の図で試せます。

1つのファイルに、3つの役割

# mise.toml（例）
[tools]
node = "24"      # 24 で始まる版

[env]
_.file = ".env"  # .env を読む

[tasks.test]
run = "..."      # mise run test で実行
Dev tools（ツール）Node.js・Python・Go・Terraform など多数のツールを入れ、フォルダごとに版を切り替える
Environments（環境変数）フォルダに入ったときに環境変数を設定する。.env ファイルも読める
Tasks（タスク）ビルドやテストのコマンドに名前を付けて実行する。依存関係も書ける

公式サイトは、マシン全体の準備をする Bootstrap も挙げています。設定ファイルは今いるフォルダに近いものほど優先され、個人だけの設定は Git に入れない mise.local.toml に書きます。"24" のような幅のある指定を正確な版に固定するのが、ロックファイル mise.lock です。

試してみる: どこから呼ぶと、どの版が動くか

project-a は Node.js の 20 系、project-b は 24 系を mise.toml に書いた例です（環境変数 APP_MODE も [env] に書いてあるとします）。フォルダ・呼ぶ場所・切り替え方を選んで、動く版を比べてください。版と変数は説明のための例です。

どこから呼ぶか
切り替え方
project-a/
[tools]
node = "20"

APP_MODE = "a"

node = "24"

project-a の版（20 系）project-b の版（24 系）mise の切り替えが効かない

試してみる: ロックファイルで、全員の版をそろえる

mise.toml に node = "24" とだけ書いたプロジェクトを、2人の開発者と CI が別の時期に入れる例です。"24" は「24 で始まる版」なので、入れた時期によって解決される版が変わりえます。版の番号は説明のための例です。

得るもの

  • 道具の集約: 言語ごとのバージョンマネージャー、環境変数の切り替え、タスクの実行を、1つの道具と1つのファイルにまとめられる
  • 再現性: mise.toml と mise.lock を Git に入れれば、開発者と CI が同じ版を使える
  • 段階的な移行: .tool-versions を読めるので、asdf からはプロジェクトごとに移せる

代わりに失うもの・注意点

  • 隔離はしない: PC の上で直接ツールを切り替えるだけで、OS のライブラリの違いまではそろわない（筆者の見立て）
  • 入手先の信頼: 検証の強さはバックエンドしだい。asdf のプラグインは、その作者のコードを手元で動かすことになる
  • 設定ファイルがコードを動かす: 環境変数・フックなど、コードを実行しうる部分は信頼したプロジェクトでだけ読まれる。ツールの版の指定とタスクの定義は、信頼しなくても読まれる。また mise install・mise exec・mise run を実行するとそのプロジェクトは信頼済みになるので、知らないリポジトリでは先に設定とタスクを読む
  • 保守の体制: 作者の Jeff Dickey さんが中心となって保守している。長く使う前提なら、開発が続いているかを見ておく（筆者の見立て）

導入するときに決める5つのこと

Thoughtworks は mise を Adopt に置き、チームの開発環境をそろえるときの標準の選択肢として勧めています。始める前に決めておくことです。

まとめる効果はあるか？

複数の言語や複数のサービスを抱えるチームほど、まとめる効果が大きい。1つの言語だけなら、その言語の標準の道具で足りる場合もある（筆者の見立て）。

どの OS で使うか？

macOS・Linux・Windows に対応。Windows では asdf のプラグインが動かず、GUI のアプリから使うには shim のフォルダを Path に足す必要がある。

CI でどう入れるか？

GitHub Actions 向けの公式のアクション（jdx/mise-action）がある。CI ではシェルの activate は不要で、mise run や mise exec を使う。

どこまで版を固定するか？

固定するなら mise.lock をコミットし、--locked で入れる。公式は、公開元のビルド済みのリリースを取るバックエンドを優先し、プラグインを最後にする順を勧めている。検証の有無はツールごとに mise tool で確かめる。

今の道具とどう並べるか？

.tool-versions などを残したまま始められる。mise と asdf でツールの置き場所を共有しない点に注意する。

関連技術・代替技術

asdf

複数の言語の版を1つの道具で切り替える、mise の先輩にあたる道具。設定ファイル .tool-versions は mise も読める。

direnv

フォルダに入ると環境変数を切り替える道具。mise の [env] と役割が重なる（筆者の見立て）。

Dev Container や Nix

OS のライブラリまで含めて環境を丸ごとそろえる方法。隔離や再現性は強い反面、準備の手間は大きくなる（筆者の見立て）。

ソフトウェアに署名し、署名を確かめる道具。Thoughtworks は、mise の供給網の安全の仕組みの例として、Cosign と GitHub の artifact attestations を挙げている。

用語（タップで開く）

下線の字は元の語（英単語・略語）で、＝のあとがその意味、または略語の元の綴りです。覚えるための手がかりにしてください。

バージョンマネージャー

version ＝ 版 ／ manager ＝ 管理するもの

同じツールの複数の版を1台の PC に並べて入れ、プロジェクトや場面に応じて使う版を切り替える道具。

環境変数

environment variable ＝ 環境の変数

プログラムの外から設定して、プログラムに渡す名前つきの値。接続先や動き方の切り替えに使う。

TOML

TOML ＝ Tom's Obvious, Minimal Language（Tom の、分かりやすく最小限の言語）

設定ファイルを書くための書式。mise.toml はこの書式で書く。

CI

CI ＝ Continuous Integration（継続的な統合）

変更のたびに、自動でビルドやテストを行う仕組み。

PATH

path ＝ 道・経路

コマンド名を打ったときに、その実行ファイルを探しに行くフォルダの一覧を持つ環境変数。先に書かれたフォルダが優先される。

activate

activate ＝ 有効にする

mise では、シェルにフックを入れて、フォルダの移動などに合わせて PATH と環境変数を書き換える方式。

shim

shim ＝ すき間に挟んで高さを合わせる薄い板

本物のコマンドの代わりに呼ばれ、条件に応じて本物の版を選んで起動する小さな代理のプログラム。

チェックサム

check ＝ 確かめる ／ sum ＝ 合計

ファイルの内容から計算した短い値。計算し直して一致すれば、途中で壊れたり書き換えられたりしていないと分かる。比べる元の値が信頼できる入手先のものであることが前提。

来歴（provenance）

provenance ＝ 出どころ・由来

ソフトウェアが、どのソースから、どこで、どうビルドされたかを示す証明。偽物の配布を見分けるのに使う。

ロックファイル

lock ＝ 錠をかける・固定する ／ file ＝ ファイル

「24 系」のような幅のある指定を、実際に使った正確な版に固定して記録したファイル。全員が同じ版を入れられる。

供給網（サプライチェーン）の安全

supply chain ＝ 供給の鎖

自分が使うソフトウェアや部品が、作られてから手元に届くまでに改ざんされていないことを守る考え方。
