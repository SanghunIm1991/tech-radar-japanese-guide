Mutation testing

名前の手がかり: Mutation 突然変異 ＋ testing 試すこと

プログラムにわざと小さな「バグ」を埋め込み、テストが見つけられるかで、テストそのものの質を測る手法

return a+-breturn a + b → return a - b← 1文字だけ変えた版（ミュータント）

たとえるなら

警備員の実力を確かめる、抜き打ちの訓練

わざと偽の不審者を紛れ込ませてみて、見つけられなかった者が警備の穴を教えてくれます。ミューテーションテストでは、ツールがプログラムに小さな変更を1つ加えた版（ミュータント）を自動で作り、テストがそれを見つけられるか（テストが失敗するか）を確かめます。

テストの良し悪しを測るときの2つの課題と、ミューテーションテストの答え

課題と、その答えを対で並べています。

カバレッジは「実行した」ことしか分からない

コードカバレッジ（code coverage）

何割の行が実行されたかは分かっても、結果が正しいかをテストが確かめたかは分からない。極端な例では、結果を何も確かめないテストでも、100%になりうる。

誤りを見つけられるかを、直接数える

わざと誤りを埋め込んだ版でテストを動かし、テストが失敗した（見つけた）割合をスコアにする。結果を確かめないテストは、誤りを埋め込んでも失敗しないので、見逃し（生き残り）として表れる。下の図で試せます。

AI が書いたテストで、数字が水増しされる

AI が生成したテスト

AI がコードとテストを大量に書くと、浅いテストでもカバレッジの数字は簡単に上がる（Thoughtworks の指摘）。

ロジックを変えたら落ちるかで確かめる

生き残ったミュータントが、ロジックを変えても通ってしまうテストの場所を示す。Thoughtworks は、生成されたテストがロジックの変化を見逃したまま通らないようにする安全装置と位置づけ、AI のエージェントが作業の途中で自分で回せるようになったことも挙げている。

試してみる: カバレッジが100%になっても、誤りを見つけるとは限らない

最初はテストが無い状態です。テストのボタンを①から順に選ぶと、テストが増えます（選んだ段階までのテストを、全部まとめて動かします）。カバレッジ（実行した行の割合）と、ミュータントを見つけた数を比べてください。関数・テスト・ミュータントは、説明のために作った例です。

テストする関数

function canVote(age) {
  return age >= 18;
}

テスト（上から順に足していく）

コードカバレッジ0%
ミュータントを見つけた数4つのうち 0

ツールが作ったミュータント（どれも1か所だけ変えた版）

age > 18境界を1つずらす生き残った
age < 18条件を逆にする生き残った
return true戻り値を変える（常に true）生き残った
return false戻り値を変える（常に false）生き残った
見つけた（killed: テストが失敗した）生き残った（survived: テストの穴）

テストなし: テストがまだ無いので、関数の行は一度も実行されず、カバレッジは0%です。ミュータントを入れても失敗するテストが無いので、4つとも生き残ります。

得るもの

  • 「テストが通った」を信じてよいかの裏付け。テストが本当に誤りを見つけられるかを、数字で確かめられる
  • 生き残ったミュータントが、テストの確かめ方が甘い場所を具体的に示す
  • AI に大量のテストを書かせるときの点検に使える

代わりに失うもの

  • 時間がかかる: ミュータントの数だけテストを実行する。PIT のドキュメントも、計算の負担が大きいと明言している
  • 等価ミュータント: 変えても動きが変わらないミュータントは、どんなテストでも見つけられず、スコアが100%に届かない原因になる
  • 読み解きの手間: 生き残りが「テストの穴」か「等価ミュータント」かは、人（または AI）が見て判断する（筆者の見立て）
  • スコアを目標にしすぎる危険: 数字だけを追うと、意味の薄いテストで数字を上げる方向に流れかねない（筆者の見立て）

導入するときに決める5つのこと

Thoughtworks はこの手法を Adopt に置いています。使うかどうかより、どこに、どう組み込むかを決めるのが要点です（筆者の見立て）。次の5つは、そのときに考えることです。

どこに使うか？

全部のコードに毎回かけるのではなく、間違えると影響の大きい中核の業務ロジックから始める。

Thoughtworks も、対象のパッケージを絞るか、最近変えたコードだけを確かめるよう勧めている

時間をどう抑えるか？

前回の結果を使い回し、変更の影響を受けた部分だけを実行し直すインクリメンタルな実行を使う。

StrykerJS にはインクリメンタルモードがある。PIT のインクリメンタル分析は実験的な機能の扱い（2026-11 時点）

CI にどう組み込むか？

毎回の変更で回すか、夜間にまとめて回すか。スコアの下限でビルドを失敗させるなら、等価ミュータントを考えに入れて下限を決める。

言語に合うツールはあるか？

使っている言語・テストの道具に対応したツールがあるかを確かめる（下の道具の例）。

AI とどう組み合わせるか？

AI にテストを書かせているなら、生成されたテストが本当に結果を確かめているかの点検に使えるかを考える。

実現するための道具の例

推奨でも網羅でもない例です（2026-11-15 の時点）。商用の製品は、公式の説明を確かめられたものが無かったので載せていません。

StrykerJSOSS（Apache-2.0）

JavaScript・TypeScript 向け。Stryker には C#（Stryker.NET）・Scala（Stryker4s）向けもある。

PIT（Pitest）OSS（Apache-2.0）

Java など JVM 向け。行のカバレッジをもとに、変更した箇所に向けたテストを選んで実行する。

cargo-mutantsOSS（MIT）

Rust 向け。cargo のサブコマンドとして動く。CI の説明に、プルリクエストのインクリメンタルなテストが載っている。

mutmutOSS（BSD-3-Clause）

Python 向け。前回からソースが変わった関数のミュータントだけを試し直す。Windows では WSL（Windows の中で Linux を動かす仕組み）の中で動かす。

InfectionOSS（BSD-3-Clause）

PHP 向けのミューテーションテストの枠組み。

AI がコードとテストを大量に書く時代には、カバレッジの数字は簡単に水増しできるため、テストが本当に誤りを見つけられるかを確かめるミューテーションテストが安全装置（ガードレール）として働くと、Thoughtworks は見ています。AI のエージェントが作業の中で自分で回し、テストの確かめ方を評価できるようになった点も挙げ、時間がかかるので、対象を特定のパッケージや最近の変更に絞るよう勧めています。

用語（タップで開く）

青い字は元の語（英単語・略語・名前の元になった語）で、＝のあとがその意味、または略語の元の綴りです。覚えるための手がかりにしてください。

アサーション

assertion ＝ 断言

テストの中で「結果はこうなっているはず」と確かめる部分。これが無いテストは、動かすだけで何も確かめない。

コードカバレッジ

code ＝ プログラム ／ coverage ＝ 覆う範囲

テストを実行したときに、プログラムのどれだけの部分（行や分岐）が実行されたかの割合。

ミュータント

mutant ＝ 突然変異体

元のプログラムに小さな変更を1つ加えた版。わざと埋め込んだバグにあたる。

ミューテーション演算子

mutation ＝ 突然変異 ／ operator ＝ 演算子・操作するもの

ミュータントを作るための変更の種類。「+ を − に変える」「条件を逆にする」など。

ミューテーションスコア

score ＝ 得点

有効なミュータント（コンパイルできて動いたもの）のうち、テストが見つけたものの割合（Stryker の定義。ツールによって数え方が少し違う）。高いほどテストが誤りに敏感。

等価ミュータント

equivalent ＝ 等しい ／ mutant ＝ 突然変異体

変更しても動きがまったく変わらないため、どんなテストでも見つけられないミュータント。

インクリメンタル

incremental ＝ 少しずつ増える

前回の結果を使い回し、変更の影響を受けた部分だけを処理し直すこと。時間を短くできる。

CI

CI ＝ Continuous Integration（継続的な統合）

コードを変更するたびに、ビルドやテストを自動で実行する仕組み。

JVM

JVM ＝ Java Virtual Machine（Java の仮想の機械）

Java や Kotlin、Scala などのプログラムを動かす土台。

WSL

WSL ＝ Windows Subsystem for Linux（Linux のための Windows の下位の仕組み）

Windows の中で Linux の環境を動かす仕組み。

プルリクエスト

pull request ＝ 取り込みの依頼

自分の変更を取り込んでほしいと頼む、GitHub などの仕組み。変更の確認や自動テストの起点になる。

プロパティベーステスト

property ＝ 性質 ／ based ＝ もとにした

「どんな入力でもこの性質が成り立つはず」と書いておき、入力をたくさん自動で作って確かめるテストの手法。
