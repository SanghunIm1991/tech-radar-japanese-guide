## 1. 一言でいうと

Managed agents runtime は、ソフトウェア開発の作業をする **AI エージェント**を、開発者の手元のパソコンではなく、**管理された実行基盤**（クラウドのサービスや、組織が用意した共通の基盤）の上で動かす手法です。基盤は、エージェントの繰り返しの処理、隔離された実行環境、作業の起動のきっかけ、認証情報の扱い、作業の状態の保存、動きの記録などを引き受けます（この手法の定義は [Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/managed-agents-runtime) による）。

たとえるなら、各自の机でプログラムを動かすのをやめて、社内のサーバールームに作業用の部屋を用意し、そこで決まった手順のもとに働いてもらうようなものです。人は依頼を出し、出来上がったもの（多くはプルリクエスト）を確かめます（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

コーディングエージェントを手元のパソコンで動かすと、次のような限界にぶつかります（筆者の見立て）。

- **長い作業に向かない**: パソコンを閉じれば止まる。何時間もかかる作業や、夜間の作業を任せにくい
- **並べて動かしにくい**: 同時にいくつもの作業を任せると、手元の資源と注意が足りなくなる
- **安全の管理がばらばら**: 認証情報や、エージェントが触れてよい範囲の設定が、開発者ごとに違う
- **きっかけが人に限られる**: 課題の登録、パイプラインの失敗、決まった時刻など、人が端末の前にいないときの出来事で作業を始められない

こうした作業を「依頼したら裏で進み、終わったら結果が届く」形にするには、エージェントを動かす場所を共通の基盤に移す必要があります。

## 3. 仕組みの概要

基盤が引き受ける主なものは、次のとおりです（Radar の項目の定義をもとに筆者が整理。各社の製品にも同様の機能がある）。

| 役割 | 内容 |
|---|---|
| エージェントの繰り返しの処理 | 考える→ツールを使う→結果を見る、を回す部分 |
| 隔離された実行環境 | コードを動かしても外に害が及ばない、作業ごとの環境（サンドボックス） |
| 起動のきっかけ | 課題・チャット・パイプライン・決まった時刻などから作業を始める |
| 認証情報の扱い | リポジトリや外部のサービスへの権限を、決まった範囲で渡す |
| 状態の保存 | 長い作業を止めたり再開したりできるように、経過を保存する |
| 動きの記録 | 何をしたかを後から確かめられるログ |

利用者の側が決めるのは、使うモデル、指示（プロンプト）、使わせるツールやスキルなどです。

**例1: Claude Managed Agents（Anthropic）**

あらかじめ作られた、設定を変えられるエージェントの実行基盤を、Anthropic が管理する基盤の上で動かすサービスで、長い作業や非同期の作業に向くとしています。確認日の時点ではベータ版です（[Claude Managed Agents: Overview](https://platform.claude.com/docs/en/managed-agents/overview)。この例の出典は同じ）。

- **4つの概念**: エージェント（モデル・システムプロンプト・ツール・MCP サーバー・スキルの定義）、環境（Anthropic が管理するクラウドのサンドボックスか、自前のサンドボックス）、セッション（作業を進めている1つのエージェント）、イベント（利用者の発言・ツールの結果・状態の変化）
- **組み込みのツール**: コマンドの実行、ファイルの読み書きと検索、Web の検索と取得（許可・拒否するドメインの一覧で絞れる）、MCP サーバー
- **長い作業**: セッションは途中で止めても再開でき、会話の履歴・サンドボックスの状態・出力はサービスの側に保存されます。動いている途中で追加の指示を出したり、止めたりもできます。決まった時刻に動かす設定もあります
- **データの扱い**: セッションの記録は削除するまで残り、データを保存しない契約（Zero Data Retention）の対象外です

**例2: GitHub Copilot のクラウドでの作業**

GitHub の Copilot は、クラウドの開発環境で、裏でファイルを編集し、テストやリンター（コードの書き方の点検）を動かせます。環境は、クラウドのサンドボックス、GitHub Actions を使う環境、自前の環境への接続（Remote）の3つから選びます。作業の記録で何をしたかを確かめられますが、GitHub はその記録が自分のレビューやテストの代わりにはならないとしています。GitHub Actions を使う作業は、最大で59分で打ち切られます（[GitHub Docs: Copilot on GitHub.com](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)）。

Radar は、ほかに Cursor のクラウドのエージェントと、OpenAI Codex のクラウドでの作業も例に挙げています（[OpenAI Codex の解説](../tools/openai-codex.md)）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: エージェントを「個人の道具」から「組織の基盤の上で動く仕事の担い手」に変える手法です。CI/CD（変更を自動でビルド・テスト・配備する仕組み）を各自の手元から共通のサーバーに移したのと似た流れです（筆者の見立て）。

[Coding harness for general-purpose agents](coding-harness-for-general-purpose-agents.md) が「エージェントの実行の層を自分で作るか借りるか」の話だとすれば、こちらは「その実行の層をどこで動かし、誰が運用するか」の話です（筆者の見立て）。

**得られるもの**

- **非同期の作業**: 依頼したら裏で進み、手元を空けておける（Claude Managed Agents の説明も、長い作業と非同期の作業向けとしている）
- **並列に動かせる**: 作業ごとに環境が分かれるので、複数の作業を同時に任せやすい（筆者の見立て）
- **統制と記録**: 権限・ネットワーク・ログを、基盤の側でまとめて決められる（筆者の見立て）

**代わりに失うもの・注意点**

- **データの置き場所**: クラウドのサービスでは、コードや会話の記録がサービスの側に保存される。Claude Managed Agents のように、データを保存しない契約の対象外のものもある（第3節）
- **費用の見え方**: トークンの料金に加えて、実行環境の使用時間などがかかる場合がある。作業を多く並べるほど、費用が積み上がる（筆者の見立て）
- **運用の責任**: 自前の基盤なら、隔離・認証情報・更新を自分たちで守る必要がある。本番の基盤と同じ扱いが要る（筆者の見立て。[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/managed-agents-runtime)も参照）
- **時間の上限など**: 製品ごとに、作業時間やリポジトリの範囲に制約がある（例: GitHub Actions を使う Copilot の作業は59分まで。第3節）

## 5. 採用を判断するときの観点

- **作業の性質**: 長い、繰り返しの多い、結果をプルリクエストで確かめられる作業（依存関係の更新、静的解析の指摘の修正など）から始める（筆者の見立て。[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/managed-agents-runtime)も同様の例を挙げている）
- **既製のサービスか自前か**: 始めやすいのは既製のサービス。データの置き場所、セキュリティ、社内のシステムとのつなぎに制約があるなら、自前の基盤や、自前のサンドボックスを使える製品を検討する（筆者の見立て。[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/managed-agents-runtime)と第7節も参照。Claude Managed Agents は自前のサンドボックスも選べる）
- **隔離**: エージェントの動ける範囲を閉じ込める設定を確かめる（[Agent sandboxing の解説](agent-sandboxing.md)）
- **定義の管理**: エージェントの指示・ツール・権限の定義を、コードと同じくバージョン管理し、レビューを通す（筆者の見立て。[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/managed-agents-runtime)も同様に勧めている）
- **人の確認**: 結果はプルリクエストなどで必ず人が確かめる流れにする（GitHub も、作業の記録はレビューの代わりにならないとしている）

## 6. 関連技術・代替技術

- **Agent sandboxing**: エージェントの動ける範囲を閉じ込める手法（[解説](agent-sandboxing.md)）
- **Coding harness for general-purpose agents**: コーディングエージェントの実行基盤を汎用のエージェントに使う手法（[解説](coding-harness-for-general-purpose-agents.md)）
- **Claude Managed Agents**、**OpenAI Codex**、**Cursor**: Radar のこの項目のページに、関連の項目として載っています
- **代替: 手元で動かす**: 短く、対話しながら進める作業には、手元のエージェントのほうが向く（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| AI エージェント | 指示を受けて、ツールを自分で使いながら作業を何段階も進める AI の仕組み |
| 実行基盤（ランタイム） | プログラムを動かすための土台。ここでは、エージェントを動かす環境とその管理の仕組み一式 |
| マネージド | 運用（動かし続ける、更新する、守る）を提供元や専任のチームが引き受けること |
| サンドボックス | プログラムが触れられるファイルや通信の範囲を閉じ込め、外に害が及ばないようにする環境 |
| 非同期の作業 | 依頼した人が結果を待たずに別のことをしていられる作業の進め方 |
| セッション | エージェントとの一続きの作業。保存しておけば、止めたあとに再開できる |
| プルリクエスト | コードの変更を取り込む前に、ほかの人に確かめてもらうための依頼の仕組み |
| MCP | AI のアプリと外部のツールやデータをつなぐための共通の約束事（プロトコル） |
| GitHub Actions | GitHub のリポジトリで、変更などをきっかけに決めた処理を自動で動かす仕組み |
| CI/CD | 変更を自動でビルド・テストし、配備までつなげる仕組み |
| リンター | コードの書き方の誤りや、決まりに反した書き方を自動で見つける道具 |
| トークン | LLM（大規模言語モデル）が文章を数える単位。多くのサービスの料金はトークンの数で決まる |
