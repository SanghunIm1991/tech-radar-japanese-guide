## 1. 一言でいうと

Grilling は、**コーディングエージェント**（コードを読み書きし、コマンドを実行しながら開発の作業を進める AI）に、作業を始める前に、こちらの計画や設計について**徹底的に質問させる**手法です。英語の grill は「（網で）焼く」から転じて「厳しく問い詰める」の意味で、エージェントに問い詰め役をさせるわけです。

たとえるなら、腕のよい大工が工事の前に「この壁は撤去してよいですか」「コンセントはいくつ要りますか」と施主に細かく確かめるようなものです。あいまいなまま工事を始めて、あとで壁を壊し直すのを防ぎます（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

コーディングエージェントは、指示があいまいでも、それらしい解釈を選んで作業を進めてしまいがちです。たとえば「ログイン機能を足して」とだけ頼むと、認証の方式、パスワードを忘れたときの扱い、既存の利用者のデータとの関係などを、エージェントが黙って決めてしまいます。結果が意図と違えば、作り直しになります（筆者の見立て）。

もう1つの問題は、頼む側の人間も、自分の頭の中の前提に気づいていないことです。計画を言葉にして問い詰められて初めて、「そこは決めていなかった」と分かることがよくあります（筆者の見立て）。

AI に多くのコードを書かせるほど、チームがコードの中身や決定の理由を把握できなくなる、という問題もあります。Radar の2026年4月の版には、この問題を扱う Codebase cognitive debt（コードベースの認知的な負債）という項目があります（第6節）。

## 3. 仕組みの概要

スキルとは、エージェントに特定の作業のやり方を教える手順書を、フォルダにまとめたものです（一般的な説明）。代表的な実装は、Matt Pocock が公開しているスキル集 mattpocock/skills です。README は、スキルを人が呼び出すもの（user-invoked）と、エージェントも呼び出せるもの（model-invoked）に分けて説明しています（[mattpocock/skills](https://github.com/mattpocock/skills)。以下、この節の出典は同じ README）。

**grill 系のスキル**

| スキル | README の説明の要旨 |
|---|---|
| `grill-me` | 計画や設計について、設計の分かれ道（設計の木）のすべての枝が決まるまで、容赦なく質問される。コード以外の作業（productivity の分類）向けとして紹介されている |
| `grill-with-docs` | 質問しながら、プロジェクトの業務の言葉（ドメインのモデル）を整理し、用語集（`GLOSSARY.md`）や **ADR**（設計の決定の記録）をその場で更新する |
| `grilling` | 上の2つや、ほかのスキルが共通に使う、質問の進め方の部品。エージェントが作業に合うと判断して呼び出せる（人が呼ぶこともできる） |

README は、変更をしたいときは毎回 `grill-me` か `grill-with-docs` を使うよう勧めています。

**質問のあとの流れ**

同じスキル集には、質問で固まった内容を次の作業に渡すスキルもあります。会話の内容を仕様にまとめて課題の管理の道具に登録する `to-spec`、計画や仕様を作業の単位（チケット）に分ける `to-tickets`、仕様やチケットから実装を進める `implement` などです。つまり「問い詰める → 仕様にする → 分ける → 作る」という流れの入口に、grilling が置かれています。

**使い方の流れ（例）**

1. 作りたいものの概要をエージェントに伝え、grilling のスキルを呼ぶ
2. エージェントが質問し、人が答える。答えによって次の質問が変わる
3. 決まったことを、計画・仕様・ADR などの文書に残す
4. その文書をもとに、エージェントに実装させる

**やりとりの例**（筆者が作った例。実際のスキルの出力ではありません）

> 人: 社内の備品の貸し出しを管理する画面を作りたい。
> エージェント: 借りられるのは社員だけですか、それとも外部の協力会社の人も含みますか。
> 人: 社員だけ。
> エージェント: では、社員の認証は既存の社内の仕組みを使いますか、この画面で新しく作りますか。
> 人: 既存の仕組みを使う。
> エージェント: 返却の期限を過ぎたとき、通知は誰に送りますか。借りた本人だけですか、上長にもですか。
> 人: そこは決めていなかった。本人だけでいい。

1つの答えで次の質問が変わり（社員だけ → 認証の方法）、頼む側が決めていなかった点（期限切れの通知）が表に出ている点が、この手法の要です（筆者の見立て）。こうして決まったことを、最後に計画の文書にまとめさせます。

**導入**: Claude Code ではプラグインとして入れられ、Codex・GitHub Copilot・Gemini CLI などにもそれぞれの入れ方が用意されています。ライセンスは MIT です。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: 開発の工程でいえば、要件を確かめる「聞き取り」を、エージェントとの作業の最初に組み込むものです。仕様を先に書いてから実装させる進め方（仕様駆動の開発）の、さらに手前で仕様の穴を埋める役です（筆者の見立て）。

**得られるもの**

- **手戻りの削減**: あいまいな点を、コードを書く前に片付けられる（筆者の見立て）
- **前提の見える化**: エージェントが黙って置くはずだった前提が、質問として表に出る（筆者の見立て）
- **決定の記録**: `grill-with-docs` のように、質問の結果を用語集や ADR に残せば、あとから「なぜこうしたか」をたどれる（README）

**代わりに失うもの・注意点**

- **時間がかかる**: 小さな修正のたびに長い質問に答えるのは負担になる（筆者の見立て）
- **答える人の質に左右される**: 質問に正しく答えられる人がいなければ、問題が先送りされるだけ（筆者の見立て）
- **質問の質も一定ではない**: 重要でない枝ばかり掘る、逆に大事な論点を聞き漏らす、ということは起こりうる。質問が終わったことは、計画が正しいことの保証ではない（筆者の見立て）
- **答える側の負担を軽くする工夫**: 質問ごとにエージェントの推す答えを添えさせれば、答える人は確かめて選ぶだけで済み、質問の多さの負担を和らげられる（筆者の見立て）
- **結果を残さないと消える**: 会話の中で決めただけでは、次のセッションには引き継がれない。文書に書き出す段階が要る（筆者の見立て）

## 5. 採用を判断するときの観点

- **作業の大きさ**: 設計の分かれ道が多い新しい機能や、影響の大きい変更から使う。数行の修正には要らない（筆者の見立て）
- **決定を残す場所**: 質問の結果を、ADR・仕様・課題の管理の道具のどこに残すかを決めておく（筆者の見立て）
- **答える人**: 業務の知識を持つ人（企画やドメインの専門家）が答えに加われるかを考える。コード以外の作業向けとして紹介されているスキルもある（README）
- **費用**: 質問と答えの往復のぶん、トークン（LLM が文章を数える単位で、料金の基準）を使う。ただし、作り直しにかかる量に比べれば小さいことが多い（筆者の見立て）
- **導入の手間**: スキルは手順書なので、自分たちで書くこともできる。既存のスキル集を使うなら、ライセンスと更新の頻度を確かめる（筆者の見立て）
- **レビューとのつなぎ**: 質問で決まったことの要約をプルリクエストに添えれば、レビューする人も前提を共有できる（筆者の見立て）
- **依存先**: 特定のエージェントに縛られにくい。mattpocock/skills も複数のエージェントへの入れ方を用意している（README）

## 6. 関連技術・代替技術

- **mattpocock/skills**: grilling の代表的な実装（第3節）。Radar では Tools の項目として扱われています
- **Codebase cognitive debt**（Techniques、2026年4月の版で Caution）: Radar の Grilling のページの本文と関連項目の一覧から、この項目へリンクが張られています（第2節）
- **ADR（Architecture Decision Record）**: 設計の決定とその理由を、1件ずつ短い文書に残す習慣（一般的な説明）
- **計画を先に立てさせる機能**: 多くのコーディングエージェントには、実装の前に計画を示させる使い方がある。grilling は、計画を示させるだけでなく、人に質問させる点が違う（筆者の見立て）
- **代替: 人が先に仕様を書き切る**: 書き手に時間と経験があれば、従来どおりでよい（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| コーディングエージェント | コードの読み書きやコマンドの実行を自分で行いながら、開発の作業を進める AI の仕組み |
| スキル | エージェントに特定の作業のやり方を教える手順書を、フォルダにまとめたもの。必要なときに読み込まれる |
| 設計の木 | 設計で決めるべきことを、分かれ道の連なりとして木の形に見立てたもの。1つ決めると、次に決めることが変わる |
| ドメインのモデル | 対象の業務で使う言葉や、ものごとの関係を整理したもの |
| ADR（Architecture Decision Record） | 設計の決定1件ごとに、背景・決めたこと・理由・影響を短く書き残す文書 |
| 仕様 | 何を作るか、どう振る舞うべきかを書いた文書 |
| チケット | 課題の管理の道具に登録する、作業1件ぶんの単位 |
| プラグイン | スキルや設定を1つにまとめて、エージェントに入れられるようにしたもの |
| 仕様駆動の開発 | 先に仕様を書き、それをもとにエージェントに実装させる進め方 |
| トークン | LLM（大規模言語モデル）が文章を数える単位。多くのサービスの料金はトークンの数で決まる |
| 認知的な負債 | コードは増えたのに、チームがその中身や理由を理解していない状態がたまっていくこと |
