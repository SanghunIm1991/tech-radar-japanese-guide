## 1. 一言でいうと

Self-improving harness は、AI エージェントの**ハーネス**（モデルの周りを囲む仕組み。プロンプト・ツール・作業の手順・記憶・文脈の渡し方など）を、**エージェント自身に改善させる**手法です。エージェントが動いた記録（実行トレース）と評価の結果を、別のエージェントが読み、「どこで失敗したか」を見立てて、ハーネスの書き換えを提案したり、実際に書き換えたりします。

モデルの重み（学習で決まる中身）は変えません。変えるのは、モデルをどう使うかを決める「外側のコード」です。たとえるなら、選手の体（モデル）はそのままで、練習の記録を見ながら、作戦帳や道具の使い方（ハーネス）をコーチ役が書き直していくようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

同じモデルでも、ハーネスの作り方で成績が大きく変わります。Meta-Harness の論文は、ハーネスを「どの情報を保存し、取り出し、モデルに見せるかを決めるコード」と定義し、ハーネスの違いが性能を左右すると述べています（[arXiv:2603.28052](https://arxiv.org/abs/2603.28052)）。

これまでハーネスの改善は人の手作業でした。失敗の記録を読み、プロンプトを直し、ツールの説明を書き換え、また試す。この繰り返しは時間がかかり、記録が増えるほど人が読み切れなくなります（筆者の見立て）。人が記録を読んで改善を決める仕組みは、Radar では Feedback flywheel として別に扱われています（[解説](feedback-flywheel.md)）。Self-improving harness は、その「読んで直す」部分をエージェントに任せ、より自律的に回そうとするものです（[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/self-improving-harness)。第7節）。

## 3. 仕組みの概要

**基本の流れ**（筆者の整理。下の研究に共通する形）

1. いまのハーネスでエージェントに課題を解かせ、実行トレース（どのツールをどう呼び、何を見て、どう判断したかの記録）と点数を残す
2. 改善役のエージェントがトレースと点数を読み、失敗の原因を見立てる
3. ハーネスの一部（プロンプト、ツールの説明、手順など）の書き換えを作る
4. 書き換えたハーネスで課題を解き直し、点数が上がり、ほかの課題で悪くなっていない（回帰がない）ものだけを残す
5. 1に戻る

**研究の例**

- **Meta-Harness**（2026年3月）: 過去に試したすべての候補の**ソースコード・点数・実行トレース**を、改善役のエージェントがファイルとして読める形で渡し、新しいハーネスを提案させます。要旨によると、逐次に届く文章の分類（オンラインの文章分類）で既存の文脈管理の仕組みより7.7ポイント高く、使う文脈のトークン（LLM が文章を数える単位）は4分の1でした。数学の問題では、見つけたハーネス1つで、探索に使っていない5つのモデルの平均が4.7ポイント上がったとしています。要旨は、既存の手法がフィードバックを要約しすぎることを問題に挙げ、過去の経験を豊かに参照できることが効くと主張しています（[arXiv:2603.28052](https://arxiv.org/abs/2603.28052)）
- **VERSE**（2026年10月）: 改善役（最適化器）のハーネスも一緒に改善します。編集案を実際に動かして試し、失敗を再現し、疑わしい手順を少し変えて確かめる、という**実行による検証**を挟みます。要旨によると、この検証が無いと改善役の自己改善は性能を上げませんでした。プログラムの修正の課題（SWE-rebench の未見の課題）で、検証で選んだ最良のハーネスの正答率が42.3%（最も強い比較対象は39.2%）、最適化に使った課題とは傾向の違う、5つの言語の新しい課題で37.7%（同29.3%）でした（[arXiv:2610.02616](https://arxiv.org/abs/2610.02616)）

Lilian Weng の概説記事は、この分野の研究を整理しています。たとえば、改善を許す範囲をハーネスの作業場所に限り、評価の仕組みやモデルの設定は読み取り専用にして、評価そのものを無効にするようなずる（報酬ハッキング）を防ぐ研究や、既知の失敗が直ったかと、ほかの問題が起きていないかの両方で確かめてから採用する研究を紹介しています（[Lil'Log: Harness Engineering for Self-Improvement](https://lilianweng.github.io/posts/2026-07-04-harness/)、見出し「Self-Improving Harness」）。

**手元の道具で試せる形**

コーディングエージェントの中には、ハーネスを利用者がコードで拡張でき、拡張をエージェントに書かせることを想定しているものがあります。

- **Pi**: TypeScript の拡張で、ツールの追加や、ツールの呼び出しを止める・書き換えるといったフックができます。ドキュメントは、拡張を Pi 自身に作らせるよう勧めており、決まった場所に置いた拡張は `/reload` で読み込み直せます（[Pi: Extensions](https://pi.dev/docs/latest/extensions)）
- **Claude Code の Mods**: JavaScript／TypeScript のイベントの処理で、ツールの呼び出しや画面の表示に手を入れられます。作りたいものを説明すれば Claude が Mod を書く、と説明されています（[Claude Code Docs: Mods](https://code.claude.com/docs/en/plugins/mods/overview)）

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: エージェントのシステムの「改善の仕組み」の設計です。ソフトウェアでいえば、性能の測定と調整を自動で回す仕組みに近く、人が回していた改善の輪を、測定（可観測性）と書き換えのしやすさ（プログラマビリティ）を土台に自動化するものです（筆者の見立て。この2つを前提に挙げる点は [Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/self-improving-harness)も同様）。

**得られるもの**

- **改善の速さ**: 人が読み切れない量のトレースを使って、改善の候補を次々に試せる（筆者の見立て）
- **モデルを変えずに成績を上げる**: 重みの学習が要らないので、API で使う既製のモデルにも当てはめられる（筆者の見立て。上の論文は重みを固定している）

**代わりに失うもの・注意点**

- **評価への過適合**: 点数を上げることが目的になると、評価の課題にだけ効く書き換えが残りうる。改善に使う課題・選ぶための検証用の課題・最後に測る未見の課題を分ける（VERSE の論文は、検証で選んだハーネスを未見の課題で測っている）
- **報酬ハッキング**: 改善役が評価の仕組みそのものに手を出せると、点数だけを上げてしまう。書き換えてよい範囲を絞る（第3節の概説記事）
- **安全の境界**: Pi の拡張も Claude Code の Mods も、利用者と同じ権限で動く。エージェントが書いた拡張が、意図しないファイルの操作や外部への通信をしうる（Pi・Claude Code のドキュメントの注意書きに基づく筆者の見立て）
- **費用**: 書き換えのたびに課題を解き直すので、トークンと時間がかかる（筆者の見立て）
- **分かりにくさ**: 自動で積み重なった書き換えは、なぜそうなっているかを人が追いにくい。変更の履歴を残し、元に戻せるようにしておく（筆者の見立て）

## 5. 採用を判断するときの観点

- **前提がそろっているか**: 実行トレースを残す仕組みと、点数を自動で出す評価の課題（回帰テスト）があるか。無ければ、まずそちらを作る（筆者の見立て。回帰テスト付きの範囲を絞った実験を勧める点は [Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/self-improving-harness)も同様）
- **人が決めること**: 何を良くするかという目的、書き換えてよい範囲、新しい課題にも効くかの判断は、人が持つ（[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/self-improving-harness)）
- **範囲を絞って始める**: 最初はプロンプトやツールの説明など、影響の小さい部分だけを書き換えの対象にする（筆者の見立て）
- **採用の手順**: 自動の書き換えをそのまま本番に入れず、提案として人が確かめる段階を残すかを決める（筆者の見立て）
- **費用の見積もり**: 改善の1回にかかるトークンと時間を測り、得られる点数の伸びと比べる（筆者の見立て）
- **依存先**: 特定のエージェントの拡張の仕組み（Pi、Claude Code など）に寄せると、乗り換えにくくなる（筆者の見立て）

## 6. 関連技術・代替技術

- **Feedback flywheel**: 人がフィードバックを読み、何を変えるかを決める仕組み。Self-improving harness はこれをより自律的にしたもの（[解説](feedback-flywheel.md)）
- **DeepSeek Harness (DSH)**: [Radar の Self-improving harness のページ](https://www.thoughtworks.com/en-us/radar/techniques/self-improving-harness)の本文から、この項目（Tools）へリンクが張られています
- **Pi**、**Claude Code**: 同じページの関連の項目に挙がっています（第3節の拡張の仕組み）
- **代替: 人が手で直す**: トレースの量が少なく、評価の課題が整っていないうちは、人がトレースを読んで直すほうが確実（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| AI エージェント | 指示を受けて、ツールを自分で使いながら作業を何段階も進める AI の仕組み |
| ハーネス | モデルの周りを囲み、実行を取り仕切る仕組み。プロンプト、ツールとその説明、作業の手順、記憶、文脈の渡し方などを含む |
| モデルの重み | 学習で決まる、モデルの中身の数値。ハーネスの改善ではこれを変えない |
| 実行トレース | エージェントが動いたときの記録。どのツールをどう呼び、何を受け取り、どう判断したかが残る |
| 回帰（回帰テスト） | 変更によって、前はできていたことができなくなること。それを見つけるために繰り返し流すテスト |
| 可観測性 | システムの内部で何が起きているかを、記録や指標から外から分かるようにすること |
| プログラマビリティ | 部品をコードで調べたり、書き換えたり、試したりできること |
| 過適合 | 評価に使った課題にだけ合わせ込み、新しい課題では効かなくなること |
| 報酬ハッキング | 本来の目的を果たさずに、点数を上げる抜け道を見つけてしまうこと |
| トークン | LLM が文章を数える単位。料金や扱える文脈の長さの基準になる |
| LLM（大規模言語モデル） | 大量の文章で学習し、文章を読んで続きを作り出す AI のモデル |
| フック | 決まったタイミング（ツールを呼ぶ前など）に、利用者が用意した処理を差し込む仕組み |
