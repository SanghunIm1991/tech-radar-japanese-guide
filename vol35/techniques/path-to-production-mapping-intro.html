Path-to-production mapping

名前の手がかり: Path 道 to production 本番（もとは「生産」）＋ mapping 地図を作ること

開発者の端末から本番環境までの全部の手順を、関係者が集まって1枚の図に書き出し、どこで詰まっているかを見つける手法

たとえるなら

荷物の道のりを全部書き出して、「この中継所で3日も止まっている」と気づく

荷物を速く包む（コードを速く書く）だけでは、届くのは速くなりません。ソフトウェアも、書いたあとにレビュー・テスト・ビルド・検証・承認・デプロイ（配置）など多くの手順を通って、ようやく本番環境（利用者が実際に使う環境）に届きます。

本番までの道のりで起きる3つの課題と、この手法の答え

課題と、その答えを対で並べています。手順は別のチームや道具が担うことが多く、全体を見渡せている人はほとんどいません。DORA も、価値の流れ全体を見渡せている人はおらず、ほかの部分の出来事に驚くことが多いと述べています。

待ち時間が気づかれない

待ち時間（wait time）

承認待ちや、検証用の環境の空き待ちが、気づかれないまま積み重なる。

手順ごとに時間を書いて、待ちを見える形にする

関わる全員で手順を1枚に並べ、手順ごとに「受け取ってから次に渡すまでの時間（リードタイム）」と「正味の作業時間（プロセスタイム）」を書く（DORA の勧め）。2つの定義から、その差がおおよその待ち時間になる。下の図で見られます。

一部だけ速くしても、全体は速くならない

ボトルネック（bottleneck）

本当の詰まりが別の場所にあると、ある手順を速くしても全体の時間はほとんど変わらない。

端から端まで描いて、いちばん大きな待ちから直す

何日もかかる流れの中で数分を縮めても効果は小さい（DORA）。Thoughtworks も、コードを書く速さだけでなく、端から端までの流れを改善するよう勧めている。

手作業ややり方の違いが、事故を生む

ばらつき（inconsistency）

手作業の手順や、チームによって違うやり方が、事故の原因になる。

困りごとを書き出し、直す場所を見つける

手順を並べたあと、遅れ・危うさ・やり方のばらつきを困りごととして書き出す。参加者がそれまで知らなかった問題に気づく、と Thoughtworks は述べている。描いた図は、自動化できる場所を探す出発点にもなる（Martin Fowler）。

試してみる: どこを速くすると、全体が速くなるか

1つの変更が端末から本番まで届く道のりを、手順ごとの横棒で描いた例です。青は正味の作業時間、橙のしまは待ち時間です。下のボタンで改善を試し、全体の時間の変わり方を比べてください。手順・時間・困りごとは、説明のために作った例です。

ワークショップの進め方

もとになったのは、製造業のバリューストリームマッピング（トヨタが生み出した、モノと情報の流れを図にしてむだを見つける道具）です。今の状態の図を先に作り、次に目指す状態の図を作るのが基本です。

関わる人が集まる作る人から、動かし続ける人まで
手順を順に並べる端末から本番まで、共有のボードに
手順ごとに書き添える関わる人・道具・作業・できるもの
困りごとを書き出す遅れ・危うさ・やり方のばらつき
大きな詰まりから直す数字は大まかで足りる（DORA）

得るもの

  • 本番までの道のりの全体が、関わる全員に見える
  • いちばん大きな待ち（詰まり）がどこかが分かり、効く場所から直せる
  • 結合の強い部品など、自動化を妨げる設計の課題が見えてくることがある（筆者の見立て）

代わりに失うもの・注意点

  • 全員の時間: 関係者全員が集まる準備と調整の手間
  • 図はすぐ古くなる: 定期的に（たとえば半年ごとに）やり直す（DORA）
  • 一部だけを描く落とし穴: 部分最適に陥る
  • 変える権限が要る: 権限が無いと、図を作って終わりになりがち
  • 完璧を求めない: 正確な図や細かい数字にこだわると、話し合いが進まない

導入するときに決める5つのこと

Thoughtworks はこの手法を Adopt に置き、社内では標準的なやり方だとしています。上の進め方とは別に、始める前と後に決めておくことです。

誰を呼ぶか？

開発・テスト・運用・セキュリティ・承認者など、道のりに関わる全員。DORA は、すべてのチームの代表の参加が欠かせないとしている。抜けた役割の手順は、図に出てこないため（筆者の見立て）。

どこからどこまで描くか？

「開発者の端末から本番まで」を基本に、1つの変更が通る道のりを描く。

何を指標にするか？

改善の効果は DORA の5つの指標で測れる。ただし指標そのものを目標にすると、数字だけをよく見せる行動を招く（DORA の注意）。

AI で速くなった分に見合うか？

コードを書く速さが上がったなら、レビュー・テスト・デプロイの側も速くなっているかを確かめる（Thoughtworks の指摘による）。

どう続けるか？

図を作って終わりにせず、共有の場所に置いて、改善のたびに更新する。

実現するための道具の例

推奨でも網羅でもない例です（2026-11-15 の時点）。手法の中心はワークショップでの話し合いで、共有のホワイトボード（またはオンラインの同等のもの）で行えます（Radar の2022年の版の説明）。

図を描く

Miro商用のクラウドのサービス

オンラインで共有するホワイトボード。バリューストリームマップのテンプレートがある（Miro が作ったものと、利用者が作ったものがある）。

ExcalidrawOSS（MIT）。関連のサービスとして Excalidraw+ もある

手描き風の図を描く、オンラインのホワイトボード。矢印と図形で流れを描ける。

流れの時間を測る

GitLab の Value Stream Analytics商用（無料版で使えるのは一部）

開発の流れの段階ごとにかかった時間（中央値）を計算する。リードタイムや DORA の指標も表示する。

THOUGHTWORKS の評価（Vol.35・2026年11月、要旨）

社内では標準的なやり方だとしたうえで、AI のエージェントがコードを書くようになって（エージェント型のコーディング）コードを書く速さが上がると、本番までの道のりのほかの場所の詰まりが目立ったり、ひどくなったりすると、Thoughtworks は見ています。そのため、コードを書く速さだけでなく端から端までの流れを改善することが大事で、そのための手法として、あらためて重要になったとしています。

用語（タップで開く）

青い字は元の語（英単語・略語・名前の元になった語）で、＝のあとがその意味、または略語の元の綴りです。覚えるための手がかりにしてください。

ワークショップ

workshop ＝ 作業場

関係者が集まり、手を動かしながら一緒に考えたり決めたりする会。

コードレビュー

code ＝ プログラム ／ review ＝ 見直し

書いたコードを、ほかの人が読んで確かめること。

ビルド

build ＝ 組み立てる

ソースコードを、動かせる形（実行できるファイルなど）に組み立てること。

本番環境

production ＝ 生産

利用者が実際に使っている環境。これに対し、開発や検証のための環境がある。

デプロイ

deploy ＝ 部隊を配置する

作ったソフトウェアを、サーバーなどの動かす場所に配置して使える状態にすること。

ボトルネック

bottleneck ＝ 瓶の首

全体の流れの中で、いちばん詰まっている場所。ここを直さないと全体は速くならない。

バリューストリームマッピング

value ＝ 価値 ／ stream ＝ 流れ ／ mapping ＝ 地図を作ること

製品やサービスが顧客に届くまでの手順と、モノ・情報の流れを図にして、むだを見つける手法。

リードタイム

lead time ＝ 前もって要る時間

作業を受け取ってから、次に渡す（または完成する）までにかかる時間。待ち時間を含む。

プロセスタイム

process ＝ 工程 ／ time ＝ 時間

邪魔が入らず、必要なものがそろっていれば、作業にかかる正味の時間。

継続的デリバリー（CD）

CD ＝ Continuous Delivery（継続的な届け）

ソフトウェアの変更を、いつでも安全に素早く本番に出せる状態を保つ考え方と、そのための取り組み。

デプロイメントパイプライン

deployment ＝ 配置 ／ pipeline ＝ 管の道

コードの変更を、ビルド・テスト・検証を経て本番まで運ぶ一連の自動化された流れ。

DORA

DORA ＝ DevOps Research and Assessment（DevOps の研究と評価）

ソフトウェアを届ける力について調査・研究しているプログラム。その成果の指標がよく使われる。

部分最適

日本語の言葉（部分＋最適〈いちばんよい状態〉）

全体ではなく一部だけをよくしようとして、全体としては改善しない（または悪くなる）こと。
