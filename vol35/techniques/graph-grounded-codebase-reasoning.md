## 1. 一言でいうと

Graph-grounded codebase reasoning は、ソースコードやドキュメントと、その間のつながり（どの関数がどの関数を呼ぶか、どのファイルがどのファイルを読み込むか、など）を**グラフ**（点と線で関係を表したデータ）として先に作っておき、**AI のコーディングエージェント**に、ファイルを丸ごと読ませる代わりに、グラフの必要な部分だけを渡して考えさせる手法です。

たとえるなら、知らない街で目的地を探すのに、全部の通りを歩いて回る（ファイルを片端から読む）のではなく、路線図を見て乗り換えの経路を調べるようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

コーディングエージェントは、大きなコードベースを理解するとき、ファイルの名前や文字列で検索し（`grep` や `find` などのコマンド）、見つかったファイルを読む、という作業を繰り返します。この方法には弱点があります（筆者の見立て）。

- **つながりが見えにくい**: ある関数を変えたとき、どこに影響するかは、呼び出し元をたどらないと分からない。文字列の検索では、名前が違う呼び出しや、言語をまたぐ依存を見落としやすい
- **読む量が増える**: 関係を確かめるためにファイルを丸ごと読むと、**トークン**（LLM が文章を数える単位で、料金の基準）を多く使い、**コンテキスト**（一度に LLM に渡す情報）も圧迫する

ビルドやテストの構成でも、同じ問題が報告されています。Cherny-Shahar と Yehudai の論文は、リポジトリを扱うコーディングエージェントが、ビルドやテストの構造を正しくつかめず、とくに複数の言語が混ざったプロジェクトで苦労すると述べています（[arXiv:2601.10112](https://arxiv.org/abs/2601.10112)）。

## 3. 仕組みの概要

基本の流れは次のとおりです（筆者の整理）。

1. **グラフを作る**: ソースコードを構文解析し、関数・クラス・ファイルなどを**ノード**（点）、呼び出し・読み込み・継承などの関係を**エッジ**（線）として抽出する
2. **エージェントがグラフに問い合わせる**: 「この関数を呼んでいるのはどこか」「AとBはどうつながっているか」を、検索の代わりにグラフで調べる
3. **必要な部分だけを渡す**: 答えに関係する部分グラフと、該当するコードだけを LLM に渡す

**例1: Graphify**

Graphify は、コードベースと、ドキュメント・SQL のスキーマ・設定ファイル・PDF などを、1つの問い合わせ可能な知識のグラフにする道具です。ベクトルのデータベースや埋め込み（文章を数値の並びに変えたもの）は使いません（[Graphify](https://github.com/Graphify-Labs/graphify)。以下、この例の出典は同じ）。

- **コードの解析**: tree-sitter（多くの言語に対応した構文解析の道具）で、約40の言語を解析する。コードの解析は手元で行い、LLM は使わない
- **関係の種類**: ファイルをまたぐ呼び出し・読み込み・継承などのエッジを作る。各エッジには、ソースに明示されていたもの（EXTRACTED）か、Graphify が推定して解決したもの（INFERRED）かの印が付く
- **ドキュメントなど**: ドキュメント・PDF・画像は、利用者のエージェントのモデルか、設定した API の LLM で意味を読み取って、同じグラフに入れる。つまり、この部分は外部の LLM に送られうる
- **出力**: 全体のグラフ（`graph.json`）、要点をまとめた報告（`GRAPH_REPORT.md`）、ブラウザで見られる図（`graph.html`）
- **エージェントからの使い方**: Claude Code・Codex・Cursor などにスキルとして入れて呼び出せるほか、`graphify query` などのコマンド、MCP（AI のアプリとツールをつなぐ共通の約束事）のサーバーも用意されている

**例2: ビルドとテストの構造のグラフ（RIG）**

上の論文が提案する Repository Intelligence Graph（RIG）は、ソースの中身ではなく、ビルドできる部品・テスト・外部のパッケージなどと、その依存関係を、ビルドとテストの情報（CMake と CTest）から、論文の道具 SPADE が決まった手順で作るグラフです。JSON の形でエージェントに渡します。自動で作れるのは CMake のプロジェクトだけで、評価に使ったほかのビルドの仕組みのリポジトリでは、同じ形式で手作業で作っています（[arXiv:2601.10112](https://arxiv.org/html/2601.10112)）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: エージェントに渡すコンテキストを「どう選ぶか」の手法の1つです。文章の意味の近さで探す RAG（検索拡張生成）に対し、こちらはコードの構造上のつながりで探します（筆者の見立て）。

**得られるもの**

- **構造の理解**: RIG の論文では、Claude Code・Cursor・Codex の3つのエージェントに、8つのリポジトリについて30問ずつ答えさせました。RIG を渡すと、渡さない場合に比べて、正答率が平均で（相対的に）12.2%上がり、完了までの時間が53.9%短くなりました。効果は、複数の言語が混ざったリポジトリで大きかったと報告しています（[arXiv:2601.10112](https://arxiv.org/abs/2601.10112)）
- **費用**: Graphify の開発元は、クラウド版でエージェントのトークンの消費を80%減らせると主張しています（開発元の主張。[Graphify](https://github.com/Graphify-Labs/graphify)）

**代わりに失うもの・注意点**

- **いつも良くなるとは限らない**: RIG の論文の要旨も、まれに悪化した例があり、グラフを使った推論の質が引き続き重要な要因だとしています（[arXiv:2601.10112](https://arxiv.org/abs/2601.10112)）。論文の詳しい分析では、問いごとに悪化したのは1つのエージェント（Cursor）の240問中4問で、グラフを浅くしかたどらなかったことが原因とされています（[arXiv:2601.10112 の本文](https://arxiv.org/html/2601.10112)）
- **比べる相手に注意**: RIG の論文の比較の基準は、ふだんの道具（ファイルの検索など）は使えるが RIG を渡さないエージェントです。`grep` などの個別の道具と比べた実験ではありません（[arXiv:2601.10112 の本文](https://arxiv.org/html/2601.10112)）。自分の環境で確かめる必要があります（筆者の見立て）
- **グラフの鮮度**: コードが変わればグラフも作り直す必要がある。古いグラフは、誤った経路を自信を持って示しうる（筆者の見立て）
- **推定の関係**: 推定で作ったエッジ（Graphify の INFERRED）は、間違っている可能性がある（筆者の見立て）
- **外部への送信**: Graphify では、ドキュメントや画像の解析は LLM を使うため、社外秘の資料を入れるなら送信先を確かめる（第3節）

## 5. 採用を判断するときの観点

- **規模と複雑さ**: 小さなリポジトリなら、エージェントの普通の検索で足りることが多い。大きく、言語やモジュールの境界が多いほど試す価値がある（筆者の見立て。RIG の論文でも複数言語で効果が大きい）
- **測り方**: 同じ課題を、グラフありとなしで解かせ、正答率・時間・トークンを比べる（筆者の見立て）
- **更新の仕組み**: グラフをいつ作り直すか（変更のたび、コミットのたびなど）を決める。Graphify には、ファイルの変更を見て作り直す機能（`graphify watch`）、コミットやブランチの切り替えのたびに作り直す設定（`graphify hook install`）、変わったファイルだけを解析し直す指定（`--update`）がある（[Graphify](https://github.com/Graphify-Labs/graphify)）
- **データの扱い**: 手元だけで完結する部分と、LLM に送る部分を分けて把握する（第3節）
- **依存先**: 道具が新しく、出力の形式が変わりうる。グラフのファイルには形式の版が書かれているので、それを確かめる（[Graphify](https://github.com/Graphify-Labs/graphify)。後半は筆者の見立て）

## 6. 関連技術・代替技術

- **Code intelligence as agentic tooling**（Techniques、2026年4月の版で Assess）: Radar の Graph-grounded codebase reasoning のページに、関連の項目として載っています
- **普通の検索（grep・find）**: いちばん簡単な代替。比べる基準にもなる
- **言語サーバー（LSP）**: エディタが「定義へ移動」「参照の一覧」を出すための仕組み。コードの構造を問い合わせる別の手段（筆者の見立て）
- **RAG**: 意味の近さで文書を探して渡す方法。構造ではなく内容の近さを使う
- **MCP**: グラフをエージェントのツールとして公開する経路（第3節）

## 用語集

| 用語 | 説明 |
|---|---|
| グラフ | ものを点（ノード）、関係を線（エッジ）で表したデータの形 |
| ノード／エッジ | グラフの点と線。ここでは、関数やファイルがノード、呼び出しや読み込みがエッジにあたる |
| コーディングエージェント | コードの読み書きやコマンドの実行を自分で行いながら、開発の作業を進める AI の仕組み |
| コンテキスト | LLM（大規模言語モデル）に一度に渡す、指示・会話・資料などの情報の全体 |
| トークン | LLM が文章を数える単位。多くのサービスの料金はトークンの数で決まる |
| grep / find | ファイルの中の文字列や、ファイルの名前を探すコマンド |
| 構文解析 | ソースコードを読み、関数・クラス・呼び出しなどの構造に分解すること |
| tree-sitter | 多くのプログラミング言語に対応した、構文解析のための道具 |
| 埋め込み | 文章などを、意味の近さを比べられる数値の並びに変えたもの。RAG でよく使う |
| RAG（検索拡張生成） | 質問に関係のある文書を検索し、その部分を LLM に渡して答えさせる手法 |
| CMake | C や C++ などのプロジェクトで、ビルドの手順を記述・生成する仕組み |
| MCP | AI のアプリと外部のツールやデータをつなぐための共通の約束事（プロトコル） |
| 言語サーバー（LSP） | エディタに、定義の場所や参照の一覧などのコードの情報を提供する仕組みと、その約束事 |
