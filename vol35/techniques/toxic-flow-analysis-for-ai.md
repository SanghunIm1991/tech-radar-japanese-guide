## 1. 一言でいうと

Toxic flow analysis（有害な流れの分析）は、AI エージェントが使うツールの組み合わせを洗い出し、**外から入った悪意のある指示によって、秘密のデータが外へ持ち出されうる経路**を、動かす前に見つける手法です。ツールごとに「信頼できない内容を読み込むか」「秘密のデータに触れるか」「外へ送れるか」といった性質を付け、それらがつながる危険な順番（有害な流れ、toxic flow）を探します（[Invariant Labs: Toxic Flows](https://invariantlabs.ai/blog/toxic-flow-analysis)）。

たとえるなら、建物の防犯で、個々の扉の鍵を確かめるだけでなく、「外の人が入れる通用口」から「金庫室」を通って「搬出口」まで、一続きで歩ける通路が無いかを図面でたどるようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

**命取りの三点セット**

Simon Willison は、AI エージェントが次の3つを同時に持つと、データを盗まれる危険が大きくなるとして、これを「命取りの三点セット（lethal trifecta）」と名付けました（[Simon Willison: The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)。この項の出典は同じ）。

1. **秘密のデータへのアクセス**: 社内の文書、メール、非公開のリポジトリなど
2. **信頼できない内容への接触**: 攻撃者が書いた文章や画像が、モデルに届きうる経路（Web ページ、届いたメール、公開の課題票など）
3. **外へ通信する能力**: データを外に送るのに使える通信

LLM（大規模言語モデル）は、読み込んだ内容に含まれる指示にも従ってしまい、その指示が利用者からのものか、読んだ文書からのものかを確実には見分けられません。そのため、要約を頼んだ Web ページに「非公開のデータを外へ送れ」と書かれていれば、従ってしまうおそれがあります。こうした攻撃を**プロンプトインジェクション**と呼びます。

Willison は、MCP（エージェントに外部のツールをつなぐための共通の仕組み）で別々の提供元のツールを組み合わせると、この3つがそろいやすいと指摘しています。ガードレール（危険な入出力を止める仕組み）の製品にも懐疑的で、製品は「攻撃の95%を防ぐ」とうたいがちだが、Web のセキュリティでは95%ははっきり不合格だとし、確実なのはこの組み合わせ自体を避けることだとしています。

**ツールが増えると、人の目では追えない**

ツールが数個なら、どの組み合わせが危ないかを人が考えられます。しかし、エージェントに数十のツールをつなぐと、危険な順番の組み合わせは人の目では追えなくなります（筆者の見立て）。そこで、組み合わせを機械的に洗い出す方法が求められました。

## 3. 仕組みの概要

**分析の流れ**（[Invariant Labs: Toxic Flows](https://invariantlabs.ai/blog/toxic-flow-analysis)。この項の出典は同じ）

Invariant Labs（Snyk の研究部門）は、2025年7月にこの手法を発表しました。

1. エージェントが使えるツール（MCP のサーバーとその道具の設定など）を集める
2. ツールを使う順番としてありうるものを並べた**フローグラフ**（流れの図）を作る
3. 各ツールに、信頼の度合い・扱うデータの機微さ・外への送り先（持ち出しの出口）になりうるか、という性質を付ける
4. 図の中から、セキュリティの違反につながりうるツールの順番を探し、危険度の点数を付ける

ツールの設定などの静的な情報と、本番で観察した実際の動きの両方を使う分析だとしています。

**具体例**: 発表では、GitHub の MCP の悪用の例を挙げています。公開リポジトリの課題票（Issue）に悪意のある指示を書いておくと、それを読んだエージェントが、非公開のリポジトリの情報を、プルリクエストを作る形で持ち出してしまう、というものです。Willison は、1つの MCP のサーバーの中に三点セットの3つがそろっていた例として、これを挙げています（[Willison の記事](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)）。

**道具: Snyk Agent Scan**

この分析は、当初 mcp-scan という道具に試験的に組み込まれて公開されました（Invariant Labs の発表）。現在は、その流れをくむ Snyk Agent Scan があり、手元の PC にあるエージェント（Claude Code、Cursor、VS Code など）の設定から、MCP のサーバー・ツール・スキル（エージェント向けの手順書）を見つけ、プロンプトインジェクションなどを調べます（危険な組み合わせ〈toxic flows〉は、v0.5 系の検査項目に挙がっています）。ライセンスは Apache 2.0 です。使うには Snyk のアカウントが要り、ツールの名前と説明やスキルの内容を Snyk の分析の API に送ります（設定の中の秘密の値は送る前に伏せるとしています）。また、手元で動く MCP のサーバーは実際に起動して調べるため、信頼できない設定はサンドボックス（隔離した環境）で調べるよう勧めています（[GitHub: snyk/agent-scan](https://github.com/snyk/agent-scan)）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: AI エージェントの**脅威モデリング**（システムに対してどんな攻撃がありうるかを設計の段階で洗い出す手法）を、データの流れに絞って掘り下げたものです（Radar のページも同様に位置づけています）。従来のシステムで、データの流れの図を描いて、信頼の境界をまたぐ箇所を調べるのと同じ考え方です（筆者の見立て）。

**得られるもの**

- **組み合わせの危険が見える**: 1つ1つは安全なツールでも、つなぐと危険になる経路を見つけられる（Invariant Labs の発表）
- **対策の当てどころが分かる**: 危険な経路のどこを断てばよいか（外への送信を止める、信頼できない内容を読むツールを分けるなど）を決めやすい（筆者の見立て）
- **悪意のあるスキルの発見**: 便利そうに見えて、データを持ち出す隠れた指示を含むスキルを見つける用途にも使える（[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/toxic-flow-analysis-for-ai)）

**代わりに失うもの・注意点**

- **見つけるだけで防がない**: 分析は危険な経路を示すが、断つ設計は別に要る（筆者の見立て）
- **性質の付け方しだい**: どのツールを「信頼できない」「機微」とみなすかの判断を誤ると、危険な経路を見逃す（筆者の見立て）
- **道具のデータの扱い**: Snyk Agent Scan は、ツールの説明やスキルの内容を外部の API に送る。社外に出してよいかを確かめる（第3節）
- **調べる行為の危険**: 手元の MCP のサーバーを実際に起動するため、調べる対象そのものが悪意のあるものなら、調べることで害が出うる（第3節の注意書き）

## 5. 採用を判断するときの観点

- **三点セットがそろっているか**: エージェントが、秘密のデータ・信頼できない内容・外への通信の3つを同時に持つなら、分析の価値が高い（Willison の記事の考え方に基づく筆者の見立て）
- **つなぐツールの数**: ツールや MCP のサーバー、スキルが増えるほど、手作業での確認が難しくなる（筆者の見立て）
- **既存の脅威モデリングとの統合**: 新しい作業として切り離さず、いつもの脅威モデリングの中にこの観点を入れる（筆者の見立て）
- **外部への送信の可否**: 分析の道具がどんなデータを外に送るかを確かめ、社内の決まりに合うかを判断する（第3節）
- **見直しの時期**: ツールやスキルを足したり更新したりするたびに分析し直す。CI（変更のたびに検査を自動で走らせる仕組み）に組み込めるかも確かめる（筆者の見立て）

## 6. 関連技術・代替技術

- **Threat modeling**: 攻撃を設計の段階で洗い出す手法。この手法はその一部として使える（[解説](threat-modeling.md)）
- **Agent Skills**、**Agent Scan**: [Radar の Toxic flow analysis for AI のページ](https://www.thoughtworks.com/en-us/radar/techniques/toxic-flow-analysis-for-ai)の関連の項目に挙がっています
- **Agent sandboxing**: エージェントの動ける範囲や外への通信を閉じ込める手法。見つけた危険な経路を断つ手段の1つ（[解説](agent-sandboxing.md)）
- **代替: 三点セットを最初から作らない設計**: 外への通信を持たせない、信頼できない内容を読むエージェントには秘密のデータを渡さないなど、組み合わせ自体を避ける（Willison の記事の勧め）

## 用語集

| 用語 | 説明 |
|---|---|
| AI エージェント | 指示を受けて、ツールを自分で使いながら作業を何段階も進める AI の仕組み |
| LLM（大規模言語モデル） | 大量の文章で学習し、文章を読んで続きを作り出す AI のモデル |
| プロンプトインジェクション | モデルが読む文章の中に指示を紛れ込ませ、本来の利用者の意図と違う動きをさせる攻撃 |
| 命取りの三点セット（lethal trifecta） | 秘密のデータへのアクセス・信頼できない内容への接触・外への通信の3つ。そろうとデータを盗まれる危険が大きい |
| MCP | エージェントに外部のツールやデータをつなぐための共通の仕組み（Model Context Protocol） |
| フローグラフ | ツールを使う順番やデータの流れを、点と線でつないで表した図 |
| 持ち出し（exfiltration） | 秘密のデータを、許可なく外部へ送り出すこと |
| 脅威モデリング | システムに対してどんな攻撃がありうるかを、設計の段階で洗い出す手法 |
| スキル | エージェントに特定の作業のやり方を教える、手順書のようなファイル |
| サンドボックス | 外に影響が出ないよう、隔離した環境でプログラムを動かす仕組み |
| ガードレール | 危険な入力や不適切な出力を見つけて、止めたり書き換えたりする安全の仕組み |
| CI | 変更のたびに、ビルドや検査を自動で走らせる仕組み |
