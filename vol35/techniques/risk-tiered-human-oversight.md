# Risk-tiered human oversight（リスクに応じて人の確認の深さを変える）

## 1. 一言でいうと

Risk-tiered human oversight は、AI エージェントが書いたコードや、エージェントが行う操作を、**すべて同じ深さで人が確かめるのをやめ、何が壊れうるかに応じて確認の深さを段階（ティア）に分ける**手法です。危険が大きく元に戻しにくい変更は人がしっかり確かめ、危険の小さい変更は自動の検査に任せて人の手を省きます。

たとえるなら、空港の保安検査で、全員の荷物を同じように開けて調べるのではなく、検査機と危険度の判定で、開けて調べる荷物を絞るようなものです。人の注意という限られた資源を、本当に要るところに集めます（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

AI のコーディングエージェントが書くコードの量が増えると、人のレビューが追いつかなくなります。すべての変更に同じ深さの確認を求め続けると、次のどちらかに陥りがちです（筆者の見立て）。

- **形だけの承認**: 量が多すぎて中身を読まずに承認する。人が確かめた形は残るが、実際には何も守っていない
- **詰まり**: 丁寧に読もうとすると、レビューの待ち行列が延び、エージェントで速くなったはずの開発が止まる

AWS の Well-Architected（クラウドの設計の良い習慣をまとめたもの）の、エージェント型の AI 向けの観点集も、リスクにかかわらず一律に人が確かめることを、避けるべきやり方（アンチパターン）に挙げています（[AWS: AGENTREL02-BP05](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel02-bp05.html)）。

## 3. 仕組みの概要

**段階の分け方の例（AWS）**

AWS の観点集は、エージェントの行動を、影響の大きさと元に戻せるかどうかで、3つの段階に分けるよう勧めています（[AWS: AGENTREL02-BP05](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel02-bp05.html)。この項の出典は同じ）。

| 段階 | 対象 | 人の関わり方 |
|---|---|---|
| 自動 | 危険が小さく、元に戻せる行動 | 人は確認しない |
| 通知 | 危険が中くらいの行動 | 担当者に知らせたうえで進める |
| 承認 | 危険が大きい、または元に戻せない行動 | 人が明示的に承認してから進める |

人が見る前に、方針に反する行動を自動の検査で落とす層を置くことも勧めています。あわせて、承認を求めるときには、行動の説明・エージェントの判断の理由・影響の見積もり・それまでの経過をまとめて示すこと、承認が来ないときの期限と、別の人への引き継ぎや安全な既定の動きを決めておくこと、すべての判断を、誰が・なぜ・いつ判断したかとともに記録することを勧めています。この観点を満たさない場合のリスクは「高」とされています。

**コードの変更での例（Meta）**

Meta の論文は、危険の小さいコードの変更（diff）を自動でレビューして取り込む仕組み RADAR（Risk Aware Diff Auto Review）を報告しています。変更を、書いた人や出どころの種類で分け、対象にしてよいかの条件、決まった規則による検査、機械学習で求めた変更の危険度の点数、LLM による自動のコードレビュー、決まった手順での検証、という段階を順に通し、すべて通ったものだけを取り込みます（[arXiv:2605.30208](https://arxiv.org/abs/2605.30208)。この項の出典は同じ）。

要旨によると、RADAR がレビューした変更は53万5千件を超え、うち33万1千件以上が取り込まれました。RADAR がレビューした変更は、それ以外の変更と比べて、取り消し（revert）の割合が約3分の1、本番の障害の割合が約50分の1で、レビューにかかる時間の中央値は35%短くなったとしています。

**「ここは必ず人が見る」場所を決める仕組み（GitHub）**

コードの中で、決まったファイルやフォルダへの変更には必ず担当者のレビューを求める、という設定は、既存の道具でもできます。GitHub の CODEOWNERS というファイルにパスと担当者を書くと、そのパスを変えるプルリクエストで担当者にレビューが自動で依頼されます。ブランチの保護の設定で「Code Owners のレビューを必須にする」を有効にすれば、担当者の承認なしには取り込めなくなります（担当者にリポジトリへの書き込みの権限が要るなどの条件があります。[GitHub Docs: About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)）。

**組み合わせ方の例**（筆者の整理。場所の指定と LLM による振り分けを組み合わせる形は、[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/risk-tiered-human-oversight)も挙げています）

1. 認証・決済・データベースの構造など、必ず人が見る場所を、CODEOWNERS のような仕組みで決める
2. それ以外の変更は、LLM などで影響を見積もって段階に振り分ける
3. 危険の小さい段階は、テストなどの自動の検査（CI）を通れば自動で取り込む
4. 取り消しや障害の割合を見て、段階の境目を調整する

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: 開発の流れの中の「品質の関門」の設計です。テストの自動化で、すべてを手で試すのをやめて、重要な部分に人の探索的なテストを集めるのと同じ考え方を、レビューと承認に当てはめたものです（筆者の見立て）。

**得られるもの**

- **人の注意を集中できる**: 危険の大きい変更に、時間をかけたレビューを回せる（筆者の見立て）
- **流れが速くなる**: 危険の小さい変更が待たされない。Meta の論文はレビューの時間の短縮を報告している（第3節）
- **判断の記録**: 段階と承認の記録を残せば、あとから「なぜ通したか」をたどれる（AWS の観点集）

**代わりに失うもの・注意点**

- **振り分けの誤り**: LLM による影響の見積もりは間違いうる。危険な変更を「小さい」と判定すると、人の目を通らずに取り込まれる（筆者の見立て）。必ず人が見る場所を決め打ちで併用するのは、この対策になる
- **数字の読み方**: Meta の取り消しや障害の割合の差は、もともと危険の小さい変更を選んで比べた結果を含みうるので、そのまま「自動のレビューのほうが人より優れている」とは読めない（筆者の見立て）
- **自動の検査の質に依存する**: 自動で取り込む段階は、テストや静的な検査が十分でなければ成り立たない（筆者の見立て）
- **責任の所在**: 人の目を通らずに取り込まれた変更で障害が起きたとき、誰が責任を持ち、どう振り返るかを先に決めておかないと、段階の仕組みそのものへの信頼が崩れる（筆者の見立て）
- **承認の詰まり**: 承認の段階に期限や引き継ぎが無いと、エージェントが止まったままになる（AWS の観点集はこれもアンチパターンに挙げている）

## 5. 採用を判断するときの観点

- **前提の整備**: 自動のテスト・静的な検査・取り消しの手順が整っているか。整っていなければ、自動の段階を作る前にそちらを整える（筆者の見立て）
- **段階の基準**: 影響の大きさ・元に戻せるか・触れる場所（認証・お金・個人情報など）で決める（AWS の観点集の基準に筆者が例を足した）
- **小さく始める**: 最初は自動の段階を狭くし、取り消しや障害の割合を測りながら広げる（筆者の見立て）
- **記録と監査**: 誰が、どの段階で、なぜ通したかを残す（AWS の観点集）
- **費用**: LLM で変更を振り分けたり自動でレビューしたりするぶん、トークン（LLM が文章を数える単位で、料金の基準）がかかる。人のレビューの時間がどれだけ減ったかと並べて測る（筆者の見立て）
- **規制**: 業種によっては、変更の承認の手続きが規則で決まっている。自動の取り込みが認められる範囲を確かめる（筆者の見立て）

## 6. 関連技術・代替技術

- **Human-in-the-loop theater**: Radar のこの項目のページから、この項目（形だけの人の確認を戒めるもの）へリンクが張られています
- **CODEOWNERS とブランチの保護**: 必ず人が見る場所を決める仕組み（第3節）
- **Agent sandboxing**: エージェントの動ける範囲を閉じ込める手法。段階の振り分けと組み合わせて、誤りの影響を小さくする（[解説](agent-sandboxing.md)）
- **代替: すべてを人がレビューする**: 変更の量が少なければ、従来どおりでよい（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| AI エージェント | 指示を受けて、ツールを自分で使いながら作業を何段階も進める AI の仕組み |
| 段階（ティア） | 危険の大きさに応じて分けたまとまり。段階ごとに人の関わり方を変える |
| レビュー | ほかの人がコードの変更を読み、問題が無いかを確かめること |
| 差分（diff） | 2つの版のあいだで、どの行が消え、どの行が足されたかを示したもの。ここでは変更1件の単位 |
| 取り消し（revert） | 取り込んだ変更を、あとから元に戻すこと |
| CI | 変更のたびに、ビルドやテストを自動で走らせる仕組み |
| プルリクエスト | コードの変更を取り込む前に、ほかの人に確かめてもらうための依頼の仕組み |
| CODEOWNERS | GitHub で、パスごとの担当者を書いておき、そのパスの変更で担当者にレビューを自動で依頼するファイル（必須にするにはブランチの保護と組み合わせる） |
| ブランチの保護 | 決めた条件（レビューの承認、テストの成功など）を満たさないと、変更を取り込めないようにする設定 |
| アンチパターン | よくある、しかし避けるべきやり方 |
| Well-Architected | AWS がまとめた、クラウドのシステムを設計するときの良い習慣と確認の観点 |
| LLM（大規模言語モデル） | 大量の文章で学習し、文章を読んで続きを作り出す AI のモデル |
