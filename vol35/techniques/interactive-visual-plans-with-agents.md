## 1. 一言でいうと

Interactive visual plans with agents は、**コーディングエージェント**（コードを読み書きし、コマンドを実行しながら開発の作業を進める AI）に、実装の前の計画を、長い文章ではなく、**図・画面の下書き・操作の流れなどを含む、ブラウザで見て触れる文書**（HTML や MDX などで書いたもの）として作らせ、人がそれを確かめてから実装に進む手法です。

たとえるなら、家を建てる前に、文章の仕様書だけでなく、間取り図や完成予想図、模型を見せてもらってから着工を決めるようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

多くのコーディングエージェントには、実装の前に計画を示させる使い方があります。ただ、その計画は、会話の中に流れる長い文章になりがちです。変更が複数のファイルや画面、データの構造にまたがると、文章だけでは全体像がつかみにくく、読む側が細部を読み飛ばしてしまいます（筆者の見立て）。

計画を確かめるのは、エージェントが大量のコードを書く前に人が意図とのずれを止められる、数少ない機会です。その機会を活かすには、人が短い時間で「何が、どこで、どう変わるのか」を把握できる形が要ります（筆者の見立て）。

## 3. 仕組みの概要

Radar がリンクしている例は、Builder.io の公開しているスキル集 BuilderIO/skills の `visual-plan` と `visual-recap` です（[BuilderIO/skills](https://github.com/BuilderIO/skills)）。スキルとは、エージェントに特定の作業のやり方を教える手順書を、フォルダにまとめたものです（一般的な説明）。

**visual-plan（実装の前）**

エージェントが会話の中で書くはずだった計画を、人が読みやすい **MDX**（Markdown の中に、図や部品を埋め込めるようにした書式）の文書にします。含められるものとして、README は次を挙げています（[visual-plan の README](https://github.com/BuilderIO/skills/blob/main/skills/visual-plan/README.md)。この項の出典は同じ）。

- 構成の図、画面の下書き（ワイヤーフレーム）、操作できる試作
- 変更するファイルの地図、説明の付いたコード
- API の仕様（OpenAPI 風）、データの構造の図、差分
- 未決の質問、コメント

この計画は**承認の関門**として扱い、ソースコードの編集を始める前に承認するものとされています。使いどころは、複数のファイルにまたがる、あいまいな、危険の大きい、構成に関わる、データや画面の多い作業です。小さな修正や1行の変更、計画より差分を見るほうが早い変更には使わないよう README は勧めています。

**3つの置き場所の方式**

| 方式 | 内容 |
|---|---|
| ホスト型（推奨） | Agent-Native の計画用アプリ（plan.agent-native.com。無料・オープンソース）に置き、共有のリンクとコメントが使える。計画の内容はそのサービスのデータベースに保存される |
| 手元のファイルだけ | MDX を手元に書き出し、手元で動く中継（localhost のブリッジ）を通して、ホスト側の計画の画面で開く。表示の画面はホスト側のものを使うが、計画の内容はホスト側のデータベースに書かない。共有はできない |
| 自前のホスト | 自分で動かす計画用アプリ（または手元の開発用のトンネル）の URL につなぐ |

手元の方式では、計画をソースコードの管理に入れるなら `plans/<名前>/` のような場所に置くよう勧めています。

**visual-recap（実装の後）**

README が「visual-plan の逆」と呼ぶスキルです。ブランチ・コミット・プルリクエストの差分から、説明の付いた差分、図、API やデータの構造の要約、画面の状態の要約、レビューで見るべき点をまとめた、操作できる MDX の振り返りを作ります。大きな変更や、画面・データの構造・権限に関わる変更向けで、`--with-github-action` を付けて入れると、GitHub Actions でプルリクエストのたびに自動で作らせることもできます（[visual-recap](https://github.com/BuilderIO/skills/tree/main/skills/visual-recap)）。

**導入**: `npx @agent-native/skills@latest add --skill visual-plan` のように入れるほか、Claude Code のプラグインとしても入れられます（ただし、プラグインで入れた場合は、プルリクエスト用の GitHub Actions の設定は入りません）。ライセンスは MIT です（[BuilderIO/skills](https://github.com/BuilderIO/skills)）。

**使い方の流れ（例）**

1. 作りたいものをエージェントに伝え、visual-plan で計画を作らせる
2. 人がブラウザで図や画面の下書きを見て、コメントや質問で直させる
3. 承認してから、エージェントに実装させる
4. 実装後に visual-recap で変更をまとめさせ、レビューに使う

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: 開発の流れの中で、「計画 → 人の承認 → 実装 → レビュー」の承認とレビューの2か所を、見て分かる形にする手法です。設計のレビューで、文章の設計書だけでなく図や画面の試作を囲んで話すのと同じ発想を、エージェントとの作業に持ち込んだものです（筆者の見立て）。

**得られるもの**

- **意図のずれに早く気づく**: 画面の下書きや操作の流れを見れば、文章では読み流していた誤解に気づきやすい（筆者の見立て）
- **関係者を巻き込みやすい**: ホスト型では共有のリンクとコメントが使えるので、開発者以外の人も計画を確かめられる（visual-plan の README）
- **レビューの助け**: 大きなプルリクエストを、図と要約から読み始められる（visual-recap の README）

**代わりに失うもの・注意点**

- **作る費用**: 図や試作を含む文書を作るぶん、時間とトークン（LLM が文章を数える単位で、料金の基準）がかかる。だから README も小さな修正には使わないよう勧めている（筆者の見立て）
- **立派な計画の落とし穴**: 見た目が整っているほど、細部まで決まった気になりやすい。最初に大きく設計しすぎず、小さく確かめられる単位で計画と実装を繰り返すほうが安全（筆者の見立て。[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/interactive-visual-plans-with-agents)と第7節も参照）
- **計画と実装のずれ**: 実装の途中で計画から外れることはある。visual-recap は実際の差分をまとめるもので、計画と自動で突き合わせるとは README に書かれていない（筆者の見立て）
- **外部への送信**: ホスト型を使うと、計画の内容（コードの断片や構成の図を含む）が Agent-Native の計画用アプリのデータベースに保存される（visual-plan の README）。社外秘の情報を扱うなら、手元の方式か自前のホストを選ぶ（後半は筆者の見立て）

## 5. 採用を判断するときの観点

- **作業の大きさ**: 複数のファイルや画面にまたがる変更、データの構造や権限に関わる変更から使う（visual-plan・visual-recap の README）
- **置き場所**: ホスト型・手元・自前のどれにするかを、情報の扱いの決まりに合わせて選ぶ（筆者の見立て）
- **共有のしかた**: 手元の方式で計画を表示する URL は、そのマシンでしか開けず、共有のリンクには使えない（visual-plan の README）。チームで見るなら、計画のファイルをリポジトリに入れてプルリクエストで見せるなどの工夫が要る（後半は筆者の見立て）
- **記録として残すか**: 計画をリポジトリに入れて、あとで「なぜこう作ったか」をたどれるようにするか決める（README の `plans/` の勧めを参照）
- **承認の決まり**: 誰が計画を承認するか、承認なしに実装に進ませない運用をどう守るかを決める（筆者の見立て）
- **依存先**: 特定の開発元のスキルとサービスに頼ることになる。スキルは手順書なので、同じ考え方を自分たちで書くこともできる（筆者の見立て）

## 6. 関連技術・代替技術

- **Grilling**: 実装の前にエージェントに質問させる手法（[解説](grilling.md)）。質問で決めたことを、見える計画にまとめる、という組み合わせが考えられる（筆者の見立て）
- **計画を先に立てさせる機能**: 多くのコーディングエージェントにある、文章の計画を示させる使い方。この手法の出発点
- **ADR（Architecture Decision Record）**: 設計の決定を短い文書に残す習慣。計画の中の決定を残す先になる（一般的な説明）
- **代替: 図を人が描く**: 設計に慣れた人が、要点だけを手で図にするのも有効（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| コーディングエージェント | コードの読み書きやコマンドの実行を自分で行いながら、開発の作業を進める AI の仕組み |
| スキル | エージェントに特定の作業のやり方を教える手順書を、フォルダにまとめたもの |
| MDX | Markdown の中に、図や操作できる部品を埋め込めるようにした書式 |
| ワイヤーフレーム | 画面の配置を、色や装飾を省いて線と枠で描いた下書き |
| 試作（プロトタイプ） | 完成品の前に、見た目や操作の感じを確かめるために作る簡単な版 |
| API | プログラムどうしがやりとりするための窓口と、その約束事 |
| ブランチ | 本流のコードから枝分かれさせて、ほかに影響を与えずに変更を進めるための作業の線 |
| プルリクエスト | コードの変更を取り込む前に、ほかの人に確かめてもらうための依頼の仕組み |
| 差分（diff） | 2つの版のあいだで、どの行が消え、どの行が足されたかを示したもの |
| GitHub Actions | GitHub のリポジトリで、変更などをきっかけに決めた処理を自動で動かす仕組み |
| トークン | LLM（大規模言語モデル）が文章を数える単位。多くのサービスの料金はトークンの数で決まる |
| ADR（Architecture Decision Record） | 設計の決定1件ごとに、背景・決めたこと・理由・影響を短く書き残す文書 |
