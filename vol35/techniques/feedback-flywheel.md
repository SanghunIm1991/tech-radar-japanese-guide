## 1. 一言でいうと

Feedback flywheel は、AI のコーディングエージェントと作業して分かったこと（うまくいったこと、失敗したこと、AI に足りなかった情報）を、その場限りにせず、**チームで共有している指示ファイルや手順書に書き戻す習慣**です。書き戻すたびに次の作業が少し楽になり、その積み重ねで改善が加速していく様子を、**はずみ車**（フライホイール。一度回り始めると勢いが付いて回り続ける重い車輪）にたとえています。

たとえるなら、チームの振り返り（レトロスペクティブ）を、人どうしの働き方だけでなく、「AI に渡している説明書」にも当てはめるようなものです（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

Rahul Garg（Thoughtworks）は、AI の道具を使うチームが、ある程度のところで伸び悩むと指摘しています。うまい使い方のコツは個人の中にとどまり、同じ情報の不足や同じ失敗が繰り返されます。チームが用意した指示のファイルやコマンドは「受け身」で、自分では更新されないからです（[Garg: Feedback Flywheel](https://martinfowler.com/articles/reduce-friction-ai/feedback-flywheel.html)。以下「Garg の記事」）。

背景には、エージェントとの作業の仕方の変化もあります。Kief Morris は、エージェントの書いたコードを人が直接確かめて通す「**ループの中の人**」（human in the loop）と、エージェントを動かす仕組み一式（**ハーネス**。仕様、品質の確認、作業の手順の案内など）を整える「**ループの上の人**」（human on the loop）を区別しています。後者では、出来の悪い成果物を見つけたら、成果物そのものではなく、それを生んだハーネスを直します（[Morris: Humans and Agents in Software Engineering Loops](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)）。Feedback flywheel は、このハーネスを直す作業を、チームの決まった習慣にするものです（筆者の見立て）。

## 3. 仕組みの概要

Garg の記事の整理を例に説明します（この節の出典は Garg の記事。Backpass を除く）。

**拾う信号と、書き戻す先**

| 信号 | 例 | 書き戻す先 |
|---|---|---|
| コンテキストの信号 | AI が知らなかった情報（使っている版の注意など） | AI に最初に読ませる説明の文書 |
| 指示の信号 | うまくいった頼み方、うまくいかなかった頼み方 | チームで共有するコマンド |
| 作業の流れの信号 | うまくいった作業の順番 | チームの手順書 |
| 失敗の信号 | 何がまずかったかと、その原因 | 守らせる決まり、避けるべき書き方の文書 |

**拾う頻度**

1. **作業のたび**: 終わりに「この作業で、共有のファイルを直すべきことは起きたか」と自分に問う。プルリクエストのひな形の欄など、すでにある確認の場所に組み込む
2. **朝会**: 「昨日 AI について、皆が知るべきことを学んだ人はいるか」
3. **振り返り**: AI で何がうまくいき、何が引っかかり、何を更新するかを議題にする。最後は技術リーダーか決めた担当者が判断する
4. **定期の見直し**: 四半期ごとなどに、どのコマンドが使われ、どれが使われていないかを確かめる

**書き戻し方**: 開発者が直接直すか、エージェントに直す案を書かせて開発者が確かめます。Garg は、どちらも必須にはしないとしています。

**何を書き戻すか**: 繰り返し起きること、同じ問題に取り組む人なら誰でもぶつかることに絞ります。一度きりの特殊な例や、個人の好みは個人の範囲にとどめます。

**道具の例: Backpass**

Backpass は、手元に残っているエージェントの会話の記録を読み、役に立った指示、守られなかった指示、足りなかった指示を洗い出して、`AGENTS.md` や `CLAUDE.md`（エージェントに毎回読ませる指示ファイル）とスキルへの修正案を作る道具です。修正案には会話の記録からの引用が付き、追加・書き換え・削除には2つ以上の会話からの根拠が要ります。ファイルを書き換えるのは `backpass apply` だけで、既定では、人が修正案を1つずつ受け入れるか退けるかを選びます（[Backpass](https://github.com/kunchenguid/backpass)。MIT ライセンス）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: コードレビューで何度も出る指摘を、コーディング規約に書き足していくのと同じ発想を、エージェントへの指示や手順書に当てはめたものです。開発の工程の中では、ふだんの振り返りと、AI 向けの共有の資料の保守をつなぐ役です（筆者の見立て）。

**得られるもの**

- **個人のコツがチームのものになる**: 学びが共有の資料に入り、次の作業から全員に効く（Garg の記事）
- **同じ失敗の繰り返しを減らす**: 失敗の原因を、避けるべき書き方として残せる（Garg の記事）

**代わりに失うもの・注意点**

- **重くすると続かない**: Garg は「官僚的にならない規律」を勧め、重い手続きは捨てられると注意しています。導入を始めたばかりのチームは、まず土台（共有の資料そのもの）を作るべきだとしています（Garg の記事）
- **効果を測りにくい**: Garg は、初回の提案がそのまま受け入れられた割合、やり直しの回数、マージ後の手戻りなどを目安に挙げつつ、主に定性的なもので、ダッシュボードを作るほどではないとしています（Garg の記事）
- **資料が膨らむ**: 足すばかりだと、指示ファイルが長くなり、エージェントの判断がかえって鈍りえます。古くなった決まりを消すことも、はずみ車の一部として扱う必要があります（筆者の見立て。[Progressive context disclosure の解説](progressive-context-disclosure.md)を参照）。Radar も同様の点を強調しています（[Radar のページ](https://www.thoughtworks.com/en-us/radar/techniques/feedback-flywheel)。第7節）
- **モデルが変わると古くなる**: AI のモデルや道具が変わると、資料も古びていきます（Garg の記事）

## 5. 採用を判断するときの観点

- **規模**: 1人で使っているうちは、自分の指示ファイルを直すだけで足りる。複数の人が同じリポジトリでエージェントを使い始めたら、誰がいつ書き戻すかを決める価値が出てくる（筆者の見立て）
- **前提**: 共有の指示ファイルやコマンドがまだ無いなら、先にそれを作る（Garg の記事）
- **持ち主**: 書き戻しを最終的に判断する人を決める（Garg の記事）
- **組み込む場所**: 新しい会議を作らず、プルリクエストのひな形や振り返りなど、すでにある場に1問足す（Garg の記事）
- **自動化の度合い**: Backpass のような道具で修正案を作らせても、受け入れるかは人が決める形から始める（筆者の見立て）
- **削る基準**: 使われていないコマンドや決まりを、定期の見直しで消す（筆者の見立て）

## 6. 関連技術・代替技術

- **AGENTS.md / CLAUDE.md**: 書き戻す先になる指示ファイル
- **Agent Skills**: 手順書をフォルダにまとめる形式。書き戻す先の1つ
- **Feedback sensors for coding agents**、**Agent suggestion box**、**Context profiling**、**Self-improving harness**: Radar のこの項目のページから、それぞれの項目へリンクが張られています
- **エージェント任せのはずみ車（agentic flywheel）**: Morris が描く次の段階。エージェントに結果を見直させてハーネスの改善を提案させ、案をリスク・費用・効果で採点させる。ゆくゆくは特定の点数の案を自動で承認・適用することも考えられる、としている（[Morris の記事](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)）
- **振り返り（レトロスペクティブ）**: アジャイル開発の定番の習慣。この手法はその延長にある（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| フライホイール（はずみ車） | 重い車輪で、一度回り始めると勢いが付いて回り続ける。小さな改善が積み重なって加速する仕組みのたとえに使う |
| コーディングエージェント | コードの読み書きやコマンドの実行を自分で行いながら、開発の作業を進める AI の仕組み |
| ハーネス | エージェントを動かすための仕組み一式。仕様、品質の確認、作業の手順の案内などを含む（この解説では、AGENTS.md などの指示ファイルも含めて扱う） |
| ループの中の人（human in the loop） | AI の出力を人が1つずつ確かめてから先に進める関わり方 |
| ループの上の人（human on the loop） | 個々の出力ではなく、AI を動かす仕組みを人が整え、直す関わり方 |
| 振り返り（レトロスペクティブ） | 一定の期間の終わりに、チームで良かった点と改善点を話し合う習慣 |
| プルリクエスト | コードの変更を取り込む前に、ほかの人に確かめてもらうための依頼の仕組み |
| AGENTS.md / CLAUDE.md | エージェントが作業の初めに読み込む、プロジェクトの決まりや手順を書いた指示ファイル |
| スキル | 作業の手順・スクリプト・資料を1つのフォルダにまとめ、エージェントが必要なときに読み込めるようにしたもの |
| リファクタリング | プログラムの振る舞いを変えずに、中身を読みやすく直しやすい形に整えること |
| マージ | 変更を本流のコードに取り込むこと |
