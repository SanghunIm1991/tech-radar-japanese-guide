## 1. 一言でいうと

Agent-maintained knowledge bases は、チームの知識を、互いにリンクで結んだ**ただのテキストファイル**（Markdown）の集まりとして持ち、その**書き足しや整理をコーディングエージェントに任せる**手法です。コーディングエージェントとは、ファイルを読み書きし、コマンドを実行しながら作業を進める AI のことです。

たとえるなら、資料を受け取るたびに、担当の司書が要約を書き、関係する項目の説明を書き直し、索引を更新してくれる社内の百科事典です。人は資料を選び、質問をし、出来を確かめる役に回ります（筆者の見立て）。

## 2. 解決する課題（なぜ生まれたか）

社内の wiki は、作ったときは整っていても、だんだん古くなりがちです。新しい資料が入るたびに、関係するページを探して直し、ページどうしのリンクを張り直す手間がかかるからです（筆者の見立て）。Andrej Karpathy も、人が wiki をやめてしまうのは、この保守の負担が価値より速く増えるためで、LLM（大規模言語モデル）ならその手間をほぼかけずにこなせる、と述べています（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）。

もう1つの比較の相手は **RAG**（検索拡張生成。質問のたびに関係する文書を検索して LLM に渡す方法）です。Karpathy は、RAG は質問のたびに元の資料から知識を見つけ直し、答えが積み上がらない点を挙げています。それに対し、この手法では、資料を一度読んで整理した結果を wiki に残し、次からはそれを使います。彼はこれを、知識を一度「コンパイル」して、その後は最新に保つ、と表現しています（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）。

## 3. 仕組みの概要

Karpathy が2026年4月に公開した文書（LLM Wiki）の形を例に説明します。彼自身、この文書は細部を決めない抽象的な型だと断っています（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。以下、この節の出典は同じ）。

**3つの層**

1. **元の資料**: 記事・論文・画像・データのファイルなど、人が選んだ資料。エージェントは読むだけで、書き換えない
2. **wiki**: エージェントが書き、保守する Markdown のページの集まり。資料の要約、人物や概念ごとのページ、比較、全体の概要などからなる。人は主に読む側に回る
3. **スキーマ（決まりごと）**: wiki の構成や書き方、作業の手順を定めた文書。Claude Code なら `CLAUDE.md`、Codex なら `AGENTS.md` に書く（どちらも、エージェントが作業の初めに読み込む指示ファイル）。スキーマは、人とエージェントで少しずつ育てていく

**3つの操作**

- **取り込み（ingest）**: 新しい資料を読み、要約のページを作り、関係するページを更新する。1つの資料で10〜15ページに手が入ることもある
- **質問（query）**: エージェントが wiki を探して関係するページを読み、出典を示して答える。よい答えは、新しいページとして wiki に戻せる
- **点検（lint）**: ときどき wiki 全体を見直し、ページどうしの矛盾、古くなった記述、どこからもリンクされていないページ、足りないリンクなどを探す

**索引とログ**

- `index.md`: 全ページの一覧と1行の要約。取り込みのたびに更新し、質問のときはまずこれを読む
- `log.md`: いつ何をしたかを時系列で追記していく記録

Karpathy は、資料が100件程度・ページが数百程度までなら、この索引だけで十分に機能し、ベクトル検索の仕組みを用意せずに済むとしています。それより大きくなったら、検索の道具を足すことを勧めています。

**置き場所**

wiki はただの Markdown のファイルの Git のリポジトリなので、変更の履歴が残ります。Karpathy は、閲覧に **Obsidian** を使う例を挙げています（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）。Obsidian はノートのアプリで、**保管庫**（vault。手元のフォルダ）の中のノートを、普通の Markdown のファイルとして保存します（[Obsidian: How Obsidian stores data](https://obsidian.md/help/data-storage)）。ノートどうしは `[[ノート名]]` の形のリンクで結べ（[Obsidian: Internal links](https://obsidian.md/help/links)）、あるノートを指しているほかのノートの一覧（**バックリンク**）も表示できます（[Obsidian: Backlinks](https://obsidian.md/help/plugins/backlinks)）。エージェントにとっても人にとっても、同じファイルを読み書きできるのが要点です（筆者の見立て）。

## 4. アーキテクチャ上の位置づけとトレードオフ

**位置づけ**: 元の資料と、それを使う人・エージェントの間に置く「整理済みの知識の層」です。データ基盤でいえば、生のデータをそのまま検索するのではなく、加工した集計の表を作っておくのに近い発想です（筆者の見立て）。

**得られるもの**

- **知識が積み上がる**: 一度した整理や比較が残り、次の質問で使える（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）
- **人も読める**: 中身は普通の Markdown なので、エディタで開いて確かめ、直せる。ベクトルのデータベースのように、中身が人に見えにくい形にはならない（筆者の見立て）
- **差分で追える**: Git で管理すれば、エージェントが何をどう書き換えたかを差分で確かめ、まずい変更を戻せる（筆者の見立て）
- **仕組みが軽い**: 中規模までは、専用の検索の基盤が要らない（第3節）

**代わりに失うもの・注意点**

- **誤りが残り、広がる**: エージェントが資料を読み違えて書いた内容は、次の取り込みや質問の土台になる。RAG なら毎回元の資料に当たるが、この手法では整理した結果を信じて使うので、誤りが見つかりにくい（筆者の見立て）。元の資料を書き換えず、点検の操作を定期的に回すのは、この対策にもなる
- **規模の壁**: 索引だけで回るのは中規模までで、その先は検索の道具が要る（第3節）
- **費用**: 1つの資料の取り込みで多くのページを読み書きするため、トークン（LLM が文章を数える単位で、料金の基準）を多く使う（筆者の見立て）
- **アクセス権**: ファイルの集まりなので、細かい閲覧権限をかけにくい。見てよい人が違う情報を1つの wiki に混ぜると、エージェントの答えを通して漏れうる（筆者の見立て）

## 5. 採用を判断するときの観点

- **規模**: 個人やチームの範囲から始める。組織全体に広げるなら、書き方の決まり、持ち主、点検の頻度を先に決める（筆者の見立て）
- **人の役割**: 資料を選ぶ、質問する、エージェントの変更を確かめる、を誰が担うかを決める。Karpathy も、人の役割を資料の選定・分析の方向づけ・質問としています（[Karpathy: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）
- **変更の確かめ方**: エージェントの変更を、コードと同じくレビューしてから取り込むかどうか（筆者の見立て）
- **入れてよい情報**: 秘密情報や個人情報を資料に含めない、または置き場所を分ける（筆者の見立て）
- **依存先**: Markdown と Git だけで成り立つので、特定の製品に縛られにくい。Obsidian は閲覧を便利にする道具で、必須ではない（筆者の見立て）

## 6. 関連技術・代替技術

- **RAG**: 質問のたびに元の資料を検索する方法。比較の相手（第2節）。規模が大きい場合は組み合わせることもできる（筆者の見立て）
- **Obsidian**、**OpenWiki**、**AI-driven documentation sprawl**: Radar のこの項目のページから、それぞれの項目へリンクが張られています
- **AGENTS.md / CLAUDE.md**: エージェントに毎回読ませる指示ファイル。この手法ではスキーマを書く場所になる
- **Progressive context disclosure**: 索引を先に読み、必要なページだけを開く流れは、この手法と同じ考え方です（[解説](progressive-context-disclosure.md)。筆者の見立て）
- **代替: 人が書く wiki**: 書き手と保守の時間を確保できるなら、従来どおりでよい（筆者の見立て）

## 用語集

| 用語 | 説明 |
|---|---|
| 知識ベース | 組織やチームの知識を、探して使えるようにまとめたもの |
| コーディングエージェント | ファイルの読み書きやコマンドの実行を自分で行いながら、作業を何段階も進める AI の仕組み |
| LLM（大規模言語モデル） | 大量の文章で学習し、文章を読んで続きを作り出す AI のモデル |
| Markdown | 見出しや箇条書きを、`#` や `-` などの記号で書く、簡単な書式のテキスト |
| RAG（検索拡張生成） | 質問に関係のある文書を検索し、その部分を LLM に渡して答えさせる手法 |
| ベクトル検索 | 文章を数値の並び（ベクトル）に変え、意味が近いものを探す検索の方法。RAG でよく使う |
| スキーマ | ここでは、wiki の構成・書き方・作業の手順を定めた決まりごとの文書 |
| 保管庫（vault） | Obsidian が扱うノートを入れておく、手元のフォルダ |
| バックリンク | あるノートを指しているほかのノートからのリンク。どこから参照されているかが分かる |
| Git | ファイルの変更の履歴を記録し、差分の確認や元に戻す操作ができる仕組み |
| トークン | LLM が文章を数える単位。多くのサービスの料金はトークンの数で決まる |
