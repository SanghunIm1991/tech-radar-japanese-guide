LiteLLM

名前の手がかり: Lite 軽い ＋ LLM Large Language Model（大規模言語モデル）

OpenAI・Anthropic・Google・AWS Bedrock など100以上の LLM の提供元を、同じ形（OpenAI の API の形）で呼び出せるようにするオープンソースの道具。アプリに組み込む SDK と、組織の利用を1か所に集めるプロキシサーバー（AI ゲートウェイ）の2つの使い方がある

たとえるなら（筆者の見立て）

国ごとに形の違うコンセントに、1つの変換プラグで差し込めるようにする道具

さらにプロキシの形では、電気の使用量を部署ごとに計って上限をかける「分電盤」の役も担います。

2つの課題と、LiteLLM の答え

課題と、その答えを対で並べています。

課題1

提供元ごとに API の呼び方・応答の形・エラーの形が違い、替えるたびにコードを書き直す手間がかかる

提供元を替えたり、複数を使い分けたりするたびに書き直すのは手間（筆者の見立て）。

LiteLLM の答え

応答もエラーも、OpenAI の形にそろえて返す

応答は、どの提供元でも OpenAI の Chat Completions の形で返す。エラーも、提供元ごとの例外を、OpenAI の例外の型を受け継いだ型（認証の失敗・呼び出し回数の上限の超過など。入力が長すぎるときは、それを細かく分けた LiteLLM 独自の型）にそろえて返す。そのため、モデルの名前を替えるだけで提供元を替えられる場面が増える（筆者の見立て）。ただし、使える引数は提供元とモデルで違い、すべてがそろうわけではない。「試してみる」の図で試せます。

課題2

組織の中で利用が広がると、管理の問題が出てくる

「誰がどのモデルをどれだけ使ったか」「API キーを各チームに配ってよいか」「障害の時に別の提供元へ逃がせるか」。

LiteLLM の答え（プロキシの形）

本物の鍵を1か所に預かり、代わりの鍵を配って管理する

  • 使った量: 使った金額を、鍵・利用者・チームごとに記録し、集計して取り出せる
  • 鍵の配り方: 提供元の本物の鍵はプロキシが預かり、利用者やチームには、使えるモデル・期限・予算を決めた仮想キーを配る
  • 障害: 同じモデルを複数の配置先に置いて振り分け、失敗したら再試行し、別のモデルへ切り替える（フォールバック）設定ができる

2つの使い方と、プロキシの主な機能

Python SDK

from litellm import completion のように読み込み、関数の呼び出しで各社の LLM を使う。1つのアプリの中で提供元を切り替えたいときに向く。

プロキシサーバー（AI ゲートウェイ）

自分たちで動かす、OpenAI 互換の API を持つゲートウェイ。アプリは OpenAI の SDK の接続先をこのサーバーに向けるだけで使える。組織の LLM の利用をまとめて管理したいときに向く。

仮想キー使えるモデル・有効期限・予算・1分あたりの上限などを鍵ごとに決め、使った金額を鍵・利用者・チームごとに追える
負荷分散と予備への切り替え同じモデルを複数の配置先に置き、空いている所や応答の速い所へ振り分ける。失敗したら再試行し、別のモデルへ切り替える設定もできる
ガードレール呼び出しの前・後・同時に、入力や出力を検査する。外部の検査サービスとつなぐほか、組み込みの検査もある（鍵ごとの切り替えなど一部は有料版）
ログの連携Langfuse などの可観測性（動きを外から観察する）の道具に記録を送れる
MCP とエージェントの中継MCP（AI に外部の道具をつなぐ取り決め）のサーバーをまとめて1つの入口から提供し、鍵やチームごとに使える道具を決められる。A2A の中継にも対応する

配置: Kubernetes 向けの Helm のチャートなどで動かす。仮想キーを使うには PostgreSQL のデータベースが要り、プロキシを2台以上で動かすときは Redis を使うよう、公式が勧めている。有料版: 同じイメージに有料のライセンスキーを入れると、管理画面の SSO（5人までは無料）、監査ログ、組織やチームの管理者のロール、秘密の情報の管理サービスとの連携、鍵の自動の入れ替えなどが使える。価格は公開されていない。プロキシの処理を段階的に Rust へ移す作業が進んでいる（2026年11月の時点で途中。開発元の進み具合の表示〈39%。v1.110.0-rc.1 の時点〉は、主な API の移行の作業量を表すもので、Rust で処理している要求の割合ではない）。

トレードオフ

位置づけ: アプリと LLM の提供元の間に入る中継の層。Thoughtworks は、自社の複数のチームがモデルの呼び出しを LiteLLM に通していると書き、ライブラリというより基盤とみなすようになったため、今回の版で象限を Platforms に移したとしています。

メリット

  • 提供元を替えやすい: 呼び出し方がそろうので、モデルの差し替えや比較がしやすい
  • 管理を1か所に集められる: 鍵・予算・利用量・ログ・ガードレールをゲートウェイでまとめて扱える
  • 障害に強くできる: 再試行と予備への切り替えで、1つの提供元の障害の影響を減らせる

デメリット・注意点

  • セキュリティの更新が多い: 公式の告知の一覧には、2026年だけでも、認証を迂回されるものや、有料版のプロキシで管理者の鍵が漏れるものなど、重大度が Critical の脆弱性が複数載っている。Thoughtworks も、2026年だけで25件を超える CVE が出たことを、Adopt にしない主な理由に挙げている。ゲートウェイは全社の鍵を預かるので、速やかに更新できる体制が欠かせない（筆者の見立て）
  • 共通化の限界: 使える引数は提供元とモデルの組み合わせごとに違い、公式は、使うモデルごとに対応する引数を関数で調べるよう書いている。OpenAI の形に無い、提供元に特有の引数は、そのまま提供元へ渡される。特有の引数に頼るほど、提供元を替えやすいという利点は薄れる（筆者の見立て）
  • 捨てられる引数: 既定では、モデルが対応しない OpenAI の形の引数を渡すとエラーになる。drop_params を有効にすると、エラーの代わりにその引数を捨てる（提供元に特有の引数は対象外。プロキシでは、Claude Code と Codex からの要求に限り、既定で捨てる）。エラーで止まらない分、意図した機能が効いていないことに気づきにくくなる（筆者の見立て）
  • 中継の遅れ: ゲートウェイを通る分だけ遅れが加わる。開発元は、模擬の接続先を使った計測で、4台（各4 vCPU）で1秒あたり約1,170件の要求を処理したとき、加わる遅れは95%の要求で8ミリ秒以内（2台・約1,036件では29ミリ秒）と示している（開発元の主張）

試すときに考える5つのこと

使うかどうか、どう入れるかを考えるための観点を、詳しい解説の第5節から並べました（筆者の整理）。

SDK かプロキシか？

1つのアプリで提供元を切り替えるだけなら SDK で足りる。複数のチームの利用を管理したいならプロキシを選ぶ（筆者の見立て）。

止まったらどうなるか？

プロキシを止めると全社の LLM の利用が止まるので、複数台で動かし、PostgreSQL と Redis も含めて冗長にする（冗長化の要否は筆者の見立て）。

速やかに更新できるか？

版を固定しつつ、セキュリティの告知を購読して速やかに上げる。公式は、誰でも登録できる告知のメーリングリストを用意している。

費用は？

無料の範囲で鍵・予算・管理画面まで使える。SSO を多くの人で使う、監査ログが要る、といった場合は有料版の見積もりが要る。

秘密の情報をどう扱うか？

データベースに保存する提供元の鍵は、LITELLM_SALT_KEY で暗号化する。この値は、モデルを登録したあとは変えられない（変えると、保存した鍵を復号できなくなる）。

用語（タップで開く）

下線の字は元の語（英単語・略語）で、＝のあとがその意味、または略語の元の綴りです。覚えるための手がかりにしてください。

LLM

LLM ＝ Large Language Model（大規模言語モデル）

大量の文章で学習し、文章を生成する AI モデル。

SDK

SDK ＝ Software Development Kit（ソフトウェア開発の道具一式）

ほかのプログラムからその機能を呼び出すための部品一式。

プロキシサーバー

proxy ＝ 代理 ／ server ＝ サービスを提供する機械

利用者と相手のサーバーの間に入り、要求を中継するサーバー。中継のついでに記録や制限をかけられる。

AI ゲートウェイ

gateway ＝ 出入り口・門

アプリと LLM の提供元の間に置く中継の基盤。鍵の管理・利用量の記録・振り分け・検査をまとめて行う。

仮想キー

virtual ＝ 仮の・実体のない ／ key ＝ 鍵

本物の API キーの代わりに利用者へ配る鍵。ゲートウェイが本物の鍵に置き換えて提供元を呼ぶので、本物の鍵を配らずに済む。

例外

exception ＝ 例外・除外

プログラムの中で、エラーなどの通常と違う事態を知らせるための仕組み。種類ごとに型があり、呼び出し側は型で見分けて扱う。

フォールバック

fall back ＝ 後ろへ下がる・（別のものに）頼る

使おうとしたものが失敗したとき、あらかじめ決めた別のものに切り替えること。

ガードレール

guardrail ＝ 道路の防護柵

AI への入力や AI の出力を検査し、まずい内容を止める仕組み。

A2A

A2A ＝ Agent-to-Agent（エージェントからエージェントへ）

AI のエージェントどうしが通信するための取り決め。

CVE

CVE ＝ Common Vulnerabilities and Exposures（共通の脆弱性と露出）

公開された脆弱性に付ける共通の識別番号。

SSO

SSO ＝ Single Sign-On（一度のサインオン〈ログイン〉）

社内の認証基盤に1回ログインすれば、ほかのサービスにもログインできる仕組み。

冗長化

redundancy ＝ 余分にあること

1台が止まっても全体が止まらないよう、同じ役割のものを複数用意すること。
