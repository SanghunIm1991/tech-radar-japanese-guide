KServe

名前の手がかり: K ＋ Serve （料理などを）出す・提供する。もとの名前は KFServing

Kubernetes の上で、学習済みの AI モデルを推論のサービスとして動かすための仕組み。従来の機械学習のモデル（予測 AI）と、大規模言語モデル（LLM）の両方を扱う

たとえるなら（筆者の見立て）

料理人（モデル）の派遣会社ではなく、厨房の配置・客の案内・混雑時の増員を引き受ける「店の運営の仕組み」

料理そのもの（推論の計算）は、vLLM や Triton などの専用の実行環境が担います。

KServe の答え

宣言すれば、コントローラーが作成から削除までを管理する

InferenceService を1つ宣言すると、KServe のコントローラーが推論サービスの作成から削除までを管理し、作られた推論サービスは HTTP などの決まった形の API で呼び出せる。Knative モードでは、アクセスに応じて台数を増減し、使われていないときは0まで減らせ、カナリアで少しずつ切り替えられる。LLM では、LLMInferenceService で1台の GPU に載らないモデルを複数のサーバーで動かしたり、prefill と decode を別のサーバーに分けたりできる。ただし、HTTP のアクセスに応じた0からの起動とカナリアは Knative モードの機能で、Standard モードは対応しない。「試してみる」の図で試せます。

モデルごとに作り方がばらばらだと、モデルが増えるほど運用が重くなる

実行環境をひな形（ServingRuntime）にし、同じ書き方で公開する

モデルの形式に合う実行環境を選ばせ、形式の違うモデルも同じ InferenceService の書き方で公開できる（運用が軽くなるという評価は筆者の見立て）。Thoughtworks も、推論の実行環境とサービスの運用を切り分けて、多くのモデルを管理できる点を挙げている。「試してみる」の図で試せます。

主なリソースと、2つのモード

InferenceService1つのモデルの推論サービス。必須の predictor（推論本体）に、任意の transformer（前後の加工）と explainer（結果の説明）を足せる
ServingRuntimeモデルを動かす実行環境のひな形。名指ししなければ、自動選択を許した実行環境の中から、モデルの形式に合うものが選ばれる。クラスタ全体用の ClusterServingRuntime もある
InferenceGraph複数のモデルを順につなぐ・条件で振り分ける・結果をまとめる組み合わせを定義する
LLMInferenceServiceLLM 専用。llm-d を土台に、複数のサーバーにまたがる推論などの高度な機能を使える。API は v1alpha1（初期の段階）
Knative モード（既定）

Knative とネットワークの層（Istio を推奨。Kourier などもある）を使う。アクセスが無いときに台数を0まで減らせ、カナリアもできる。現行の文書では、主に予測 AI のモデル向け。

Standard モード

Kubernetes の標準の部品だけで動かす。生成 AI と予測 AI の両方を扱え、GPU を使う本番向け。依存が少ない代わりに、HTTP のアクセスに応じた0からの起動とカナリアには対応しない。

モデルのファイルは、S3・GCS・Azure Blob・Hugging Face などからは起動時に取り込み、Kubernetes の永続ボリュームはそのままつなぐ。OCI イメージに入れて配る方式や、サーバーのローカルのディスクに置いておくキャッシュの機能（既定では無効）もあります。

得るもの

  • モデルの運用をそろえられる: 形式の違うモデルを、同じリソースと同じ手順で公開・増減・切り替えできる（運用面の評価は筆者の見立て）
  • 実行環境を選べる: 実行環境をひな形として差し替えられるので、新しい推論エンジンが出ても乗り換えやすい（乗り換えやすさは筆者の見立て）
  • 資源の節約: Knative モードでは、使われていないモデルの台数を0にできる

代わりに失うもの・注意点

  • Kubernetes の運用力が前提: Knative モードでは、cert-manager・Knative・ネットワークの層なども入れて保守する。Kubernetes を運用していない組織には重い（筆者の見立て）
  • 0からの起動には時間がかかる: 最初の要求でコンテナの起動とモデルの取り込みを待つ。大きなモデルほど長い（筆者の見立て）
  • LLM 向けの機能は新しい: LLMInferenceService の API は v1alpha1 で、Thoughtworks も、周辺の仕組みがまだ育ちつつあると注意している
  • ドキュメントの古い箇所: 公式サイトのトップの手順には古い版の例が残っており、版ごとの手順を確かめる必要がある

試すときに考える5つのこと

使うかどうか、どう入れるかを考えるための観点を、詳しい解説の第5節から並べました（筆者の整理）。

モデルはいくつあるか？

少数なら、クラウドの推論サービスや、推論エンジンを直接コンテナで動かすほうが軽いこともある。多くのモデルや多くのチームの推論を1つの基盤にまとめたいときに効く（筆者の見立て）。

どのモードで動かすか？

予測 AI のモデルで、0台まで減らす・カナリアを使うなら Knative モード。LLM を動かす、または依存を減らしたいなら Standard モード。

LLM はどのくらい大きいか？

1台のサーバーで動くなら InferenceService（Standard モード）でも動かせる。複数のサーバーにまたがる推論、prefill と decode の分離、賢い振り分けが要るなら LLMInferenceService。

費用は？

KServe 自体はオープンソースだが、GPU のサーバーと Kubernetes の運用の人手が主な費用になる（筆者の見立て）。

実績は？

公式の採用企業の一覧には、本番で使うと示した組織が十数社載っている（網羅的ではない。掲載は、使っていることを公にしたか、掲載を許可した組織）。

Kubernetes

Kubernetes ＝ ギリシャ語で「操舵手・水先案内人」

コンテナを多数のサーバーで動かし、台数の増減や障害時の入れ替えを自動で行う基盤。

推論

inference ＝ 推し量ること

学習済みのモデルに入力を渡し、予測や生成の結果を得ること。

カスタムリソース

custom ＝ 独自に作った ／ resource ＝ 資源

Kubernetes に、標準には無い種類の設定（ここでは「推論サービス」など）を足す仕組み。

CNCF

CNCF ＝ Cloud Native Computing Foundation（クラウドネイティブのコンピューティングの財団）

Kubernetes などのクラウドネイティブの技術を育てる団体。プロジェクトは sandbox・incubating・graduated の順に段階が上がる。

予測 AI

predictive AI ＝ 予測する AI

分類や数値の予測など、決まった形の答えを返す従来型の機械学習のモデル。

LLM

LLM ＝ Large Language Model（大規模言語モデル）

大量の文章で学習し、文章を生成する AI モデル。

vLLM

製品名

LLM の推論を行うための、オープンソースの推論エンジン。KServe の Hugging Face のモデル向けの実行環境が使う。

prefill と decode

prefill ＝ 前もって満たす ／ decode ＝ （符号を）解く・取り出す

LLM の推論の2つの段階。入力の文章をまとめて読み込む段階（prefill）と、1語ずつ生成する段階（decode）。

カナリア

canary ＝ カナリア。炭鉱で危険を先に知らせるために連れて行った鳥

新しい版に一部の利用者だけを先に流し、問題が無ければ少しずつ広げる切り替え方。

OpenAI 互換の API

API ＝ Application Programming Interface（アプリをプログラムから使うための接点）

OpenAI の API と同じ形で呼び出せるようにした API。既存のアプリから呼び先を変えるだけで使える。
